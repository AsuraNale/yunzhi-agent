# task-planner · 第一步：明确任务

> 命令规矩见 AGENTS.md 第一节：`$PY` 换成 `py -X utf8`（Windows）或 `python3 -X utf8`（macOS / Linux）；所有命令在工作区根目录下跑；路径参数加双引号；交给脚本的文字先写进 `projects/_inbox/<项目名>/`。`<项目名>` 换成项目文件夹的名字，项目文件夹 = `projects/<项目名>/`。字段与格式的合同在 `toolkit/04-正本规格-v1.md`（§①、§⑨-1、§⑨-4）。

## 你在哪

研究流程四步：**①明确任务（本 skill）** → ②收集资料 → ③拟定提纲（可以省掉）→ ④撰写交付。每一步的出口都是一张卡，用户在卡上点「确认」。**确认记录、确认之后的推进都由 `card.py answer` 做，你不做。**

进来时先看 `projects/<项目名>/task_plan.md` 在不在：

- **不在** = 全新项目：直接从第 1 步做（开场检查 `projects.py status` 已经替你跑过）。
- **在**：先跑 `$PY "agent-tools/projects.py" status "<项目名>"`。`consistent` 为 false（进度和文件对不上、确认之后内容又改过）→ 停下，用一两句话告诉用户是哪份材料，等用户定，不推进。唯一的例外：`flow_change_pending` 为 true，是改流程卡还在等用户，照「变更与重新确认 · 只改流程」第 5 条做。

## 这一步怎么走

### 第 1 步 开场：一次问完

新建项目之后，你的第一条回复（说法见「对用户说话」一节）：

1. 一行交代在哪一步：一共四步，现在是第 1 步明确任务，这一步要做到什么程度；顺带说右侧能看到进度。
2. 写「先一次问完，你挑着答就行：」，下面用编号列出这个项目还没说清的三件事，各一问，照委托原话写具体：
   - **报告类型**：要下一个判断，还是先把情况梳理清楚；
   - **研究范围**：委托里最含糊的那个口径（地域层级、时间段、对象算不算）；
   - **成稿形式**：Word 版、网页版还是都要；委托没说篇幅时一并问。
3. 委托里已经写明的不再问。不逐条追问，不出考题。**不替用户拟好回答**：只问问题，不写「你可以回：……」这类让他照抄的句子（第三轮实测：助手给了一句现成的回答，用户照抄了，后来报告类型卡又把这句当成用户自己的理由来引）。
   - **这几个问题是普通对话，写在这条回复里，不调 `request_user_input`**：选项框只用来发 `card.py prepare` 准备好的卡（报告类型卡在第 3 步才出）；开场问题调了它会被守门脚本拦下，再问一遍就多出一条重复的消息（第八轮实测）。
4. 委托原话里已经写明研究范围或成稿形式的，先照第 2 步记进工作笔记，再发这条回复。

### 第 2 步 用户答了：先记进工作笔记，再回话

用户每答了研究范围或成稿形式，先用写文件的工具写（或改）`projects/<项目名>/clarify.yaml`：

```yaml
scope: 县级，含乡镇，不含村
format: Word 版
```

1. 只写这两个键：`scope` 研究范围、`format` 成稿形式，各一句用户的话，≤30 字；没答的那件不写。报告类型不写进来，它在报告类型卡上定。
2. 跑 `$PY "toolkit/scripts/clarify_check.py" "projects/<项目名>/clarify.yaml"`，退出码 0 再回话；不是 0 就照它说的改。
3. 回话先复述记下了什么（「记下了：……」那一句）；没答的，同一条消息里再一次问完。
4. 它是你的工作笔记，不是正式材料：不升版、不确认。进度页的「要聊清的三件事」在任务计划写出来之前靠它显示。

招式库（`toolkit/library/moves.md`）是工具箱不是清单：命题源自旧交付物 → 先回读上游材料；用户只给了领域没给判断 → 扇出几个切入点并亮出你的偏好；约束零散到达 → 逐条收进任务计划，写之前汇总复述一次。轻任务别做重解构；但研判型的「能用证据检验的判断」与「事先写好判定标准」不是可选的，它们在出口契约里（E1）。

### 第 3 步 报告类型卡

研究范围和成稿形式记好之后（或用户说「你先定」）：

1. 发一句话复述记下了什么，说还有一件请他在卡上定。
2. 用写文件的工具把卡上的空写进 `projects/_inbox/<项目名>/fields.json`：

```json
{"kind": "report_type", "report_name": "内参", "thesis": "下乡活动带动了县域公共充电设施增长", "why": "你说「领导就想知道这钱花得值不值」，这需要一个判断。两种写法的区别在于要不要由这份报告来证明它。", "recommend": "judge"}
```

   - `report_name` ≤6 字：成稿叫法，用用户的说法（内参、报告、研究报告……）。
   - `thesis` ≤40 字：核心判断，一句能用资料检验的话（证据可能支持，也可能推翻）；不要把委托原句直接当判断。
   - `why` ≤80 字：为什么要问。必须用「」逐字引用户的一句原话（委托原话或用户发过的消息，一字不差，脚本会核对），前面写「你说」。引的必须是用户自己的意思，优先引委托原话；用户照抄你给的句子不算（你本来就不该给）。
   - `recommend`：你推荐的那种 —— `judge`（下判断）或 `survey`（梳理情况）；不推荐就不写这个键。
   - 卡上的问题、三个选项和它们的说明都由脚本写。
3. 按 `yunzhi-card` 出卡：`$PY "agent-tools/card.py" prepare report_type "<项目名>" --fields-file "projects/_inbox/<项目名>/fields.json"`。
4. 收回答（`yunzhi-card` 第 3 步），照 `card.py answer` 的输出（用户回数字、选项名，或者「1，……」这样数字后面接一句意见，脚本都认；推荐的那一项在卡上排第一，脚本已经换算好）：
   - `selected` 为 `judge`（下判断）→ 任务计划写 `genre: argument`；`survey`（梳理情况）→ `genre: survey`；`undecided`（先不定）→ 先按 `argument` 写，在 genre_rationale 一节写明用户说先不定。说 `say` 里那句话；附了意见的（`note`），写任务计划时照做。
   - `result` 为 `note`（用户没选选项、只写了意见）→ 照 `next` 做：意见是要改卡上的核心判断或成稿叫法，说 `say_revise` 里那句、改好再出一次报告类型卡；其余先回应意见，再说 `say` 里那句（告诉用户回数字就能定），停下等用户 —— 他回数字，照 `yunzhi-card`「只写了意见之后」做，不用重新出卡。
   - `skipped`（点了跳过，或者太久没操作被自动收起）→ 说 `say` 里那句话，停下等用户；用户之后回数字，照 `yunzhi-card`「卡收起来之后」做。

### 第 4 步 写任务计划，出任务计划卡

1. 先跑 `$PY "agent-tools/projects.py" now`，拿到现在的时刻（下面写成 `<现在>`）。
2. 用写文件的工具写 `projects/<项目名>/task_plan.md`，照这个样子（规格 §①；研判型才有 hypotheses、preregistration、evidence_gate 三节，综述型不写这三节）：

````markdown
---
kind: task_plan
version: 1
updated_at: '<现在>'
genre: argument
report_name: 内参
scope_brief: H 省县级，含乡镇，不含村 · 2021–2025 年
pipeline_status: planning
budget: {cards_max: 30, steps_max: null, words_max: 8000}
evidence_standard: {inherit: true, primary_tiers: null, scope_note: null}
classification_frame: null
constraints: {words_max: 8000, formats: [docx], deadline: null}
revision_log: []
---

# 任务计划

## 原始请求 {#request}

> （委托原话，一字不改，从 projects/<项目名>/inputs/request.md 抄）

## 文体判定 {#genre_rationale}

报告类型卡上你选了「下判断」：……所以按研判型写。

## 可证伪命题 {#thesis}

（改写过的、能用证据检验的核心判断，一句）

## 假设 {#hypotheses}

- 强一点的说法：……
- 弱一点的说法：……

## 预注册结论空间 {#preregistration}

| outcome | 判定条件 | 对应表述 |
|---|---|---|
| A | （什么情况算成立） | 成立 |
| B | （什么情况算部分成立） | 部分成立 |
| C | （什么情况算不成立） | 不成立 |

## 证据对接窗口条件 {#evidence_gate}

（前提不成立时怎么收尾，例如：拿不到分县数据就停下来和你商量，改成综述型）

## 概念定义表 {#definitions}

| 概念 | 操作定义 | 不算作证据的情形 |
|---|---|---|
| …… | …… | …… |

## 项目口径 {#scope}

- 地域：……
- 时间：……
- 对象：……

## 证据标准 {#evidence_standard}

沿用默认规范：一手资料优先，来源分官方一手、机构自报、二手三类。

## 约束 {#constraints}

约 8000 字，Word 版，……

## 预算与止损 {#budget}

资料卡片不超过 30 张；超了先停下来问你。

## 要你认的三件事 {#commitments}

1. **改动内容**：这是第 1 版。
2. **最薄弱的依据**：……
3. **最可能出错的地方**：……
````

   填法：
   - `report_name` 与报告类型卡上的一字不差；没问过就照委托里用户的叫法写，用户没说就删掉这一行。
   - `scope_brief`：研究范围的一句话摘要，≤30 字，上进度页。
   - `constraints.words_max` 只写正整数，用户说的约数照数写：「八千字左右」写 8000，「两千字左右」写 2000，不自己加减（不写 2200、1800 这类数）；`budget.words_max` 写同一个数；`formats` 写用户要拿到的格式：Word 版 `docx`、网页版 `html`、两种都要 `[html, docx]`。不许照抄示例值。
   - 「对应表述」那一栏只能写 成立 / 部分成立 / 不成立。
   - 不写 `approval`（确认记录由脚本写）；`pipeline_status` 第一次写 `planning`，之后只用 `stamp.py "projects/<项目名>/task_plan.md" --advance` 改。`--advance` 只对任务计划跑；资料汇编、提纲里没有 `pipeline_status`。
   - 三点只写研究本身的事：脚本出错、工具报错、命令跑不起来这类事，从来不写进任务计划和三点，在对话里用大白话说（AGENTS.md 第四节）。
   - 三点：最后一节，恰好三条，一条一行，纯文字（不加粗内容、不放链接），改动内容 ≤60 字、最薄弱的依据 ≤60 字、最可能出错的地方 ≤80 字；第 1 版的改动内容写「这是第 1 版」。
3. 自查，两条都要过：
   - `$PY "toolkit/scripts/commitments_check.py" "projects/<项目名>/task_plan.md"` 退出码 0；
   - `$PY "toolkit/scripts/pipeline_status.py" "projects/<项目名>"` 输出里没有 `[FAIL]`。
4. 推进到等确认：`$PY "toolkit/scripts/stamp.py" "projects/<项目名>/task_plan.md" --advance gate1_awaiting`
5. 发一句话：这一版写好了、改了什么、确认之后做什么。不贴路径，不复述三点（卡上有）。
6. 按 `yunzhi-card` 出卡：`$PY "agent-tools/card.py" prepare task_plan "<项目名>" --outside none`（这一轮读过项目以外的文件，就把每个路径写成 `--outside "<路径>"`）。prepare 会顺手把这份材料换到右侧给用户看（见 `yunzhi-card` 第 2 步），不用你另外打开。版本、判定标准、三点都由脚本从任务计划里读。出卡之后、用户回答之前别动任务计划。
7. 收回答（`yunzhi-card` 第 3 步），照输出：
   - `approved` → 确认记录已经写好，进度已推进到收集资料。说 `say` 里那句交接的话（进度笔记里那一行脚本已经记了，不用你记），然后加载 `evidence-card`。
   - `not_approved` → 什么记录都没写。只写了意见、意见里没说要改什么（例如「直接帮我确认吧」）：照 `next` 不改任务计划，说 `say`，等用户回 1（不用重新出卡）。其余：照意见改；没写意见就问用户要改哪里（一次问完）。改好：`version` 加一、`revision_log` 加一条 `{v: <新版本>, at: '<现在>', who: agent, what: <改了什么>, why: <为什么>}`、三点的改动内容写这一轮改了什么 → 回到上面第 3 小步（状态已是 gate1_awaiting，不用再推进）。
   - `changed` → 说 `say` 里那句话，重新出卡。

### 第 5 步 卡没出来

`card.py prepare` 输出 `ok: false`：卡没出，照 `refuse` 和 `problems` 改（改任务计划或改 `fields.json`），再跑同一条 prepare（自己改，不用问用户）。连着三次没准备好时输出里有 `tell_user`：把 `say` 那句告诉用户，再用一句研究上的话说打算怎么改，改好再出。回答认不出（`unclear`）→ 照 `say` 问清，不许当作用户选了推荐的那项。

## 对用户说话

> 用户是政策、公共事务、产业经济方向的研究员，不是开发者。本节管你**对用户说出口的每一句话**：普通消息、对话里的提问、进度汇报、阶段交接，卡上留给你填的空，以及给用户看的材料里你自己写的句子。
>
> 本 skill 其余部分用的是内部叫法（文件名、字段名、状态名、脚本名）。干活、写文件、跑命令时照旧用；**说给用户时换成下面词表的右栏**。确认卡、决定卡上的问题、按钮和标签由出卡脚本写，你只填卡上留给你的空，填的空同样按本节写。

**五条原则**

1. 不出现英文内部词、编号和文件名：argument、E4、task_plan.md、hash 这类。需要指代某个东西时，用它的研究员名称加版本，例如「任务计划第 2 版」。
2. 每个内部对象只用一个研究员名称：任务计划、资料汇编、提纲、成稿、资料卡片、参考文献清单。不要一会儿叫正本、一会儿叫 dossier。
3. 流程动作说成「确认 / 修改 / 重新确认」，不说落章、作废、重弹、推进 collecting。
4. 检查结果只说「有什么事需要你知道或决定」，不报检查项名，也不报 PASS/FAIL。
5. 方法论的动作说成它对报告的影响。例如不说「预注册」，说「先把几种可能的结论和判定标准写下来，结论就不会随着证据被挪」。

**引用怎么写**：用户的原话逐字照抄，放进「」或整段放进 `>` 引用块，前面写明这是「你的原话」或「委托原文」；文献和报告的标题放进《》。出卡脚本会扫一遍用词，并把卡上「」里的字和用户写过的话（委托原话、用户发过的消息）逐字核对：对不上的不算引用，照样算你的用词。所以卡上填的空里，「」只放用户原话；你自己的话（包括环节名、章节名）不加引号。

**研究流程的四个环节**：明确任务 · 收集资料 · 拟定提纲 · 撰写交付。确认点：第 1 次确认（任务计划） · 第 2 次确认（资料汇编） · 第 3 次确认（提纲） · 交付确认。

**词表**（左栏是内部叫法，只在文件、命令和脚本里用；右栏是对用户的说法）

| 内部叫法 | 对用户说 |
|---|---|
| `argument` / 论证型 | 研判型（要对一个判断给出结论和依据） |
| `survey` | 综述型（梳理现状、归纳观点，不下结论） |
| 文体 · 文体判定 | 报告类型 · 定报告类型（研判型还是综述型） |
| 预注册 · 预注册结论空间 / `A/B/C` | 事先写好判定标准（动手找资料前，先写好几种可能的结论和各自的判定标准） · 几种可能的结论：成立 / 部分成立 / 不成立 |
| `H1` / `H2` | 假设一 / 假设二（或直接写「强一点的说法 / 弱一点的说法」） |
| 可证伪 / 证伪 · 证伪出口 | 能用证据检验（证据可能支持，也可能推翻） · 证据不支持时怎么收尾 |
| `thesis` / 可证伪命题 | 核心判断 |
| 升格 | 改为 |
| 闸门 / 证据对接窗口 · 闸门宣判 | 中途检查点（前提不成立，后面就不做） · 检查点的结论 |
| 操作定义 / 概念定义表 | 概念界定（怎么算、包括什么、不包括什么） |
| 变量操作化 / 构念 | 指标怎么选、怎么量 |
| 对照证据 / 强弱两套对照证据 | 正反两方面的证据 |
| 对接窗口 / 窗口 · 对接窗口1 · 对接窗口2 · 对接窗口3 · 交付对接窗口 | 确认点 · 第 1 次确认（任务计划） · 第 2 次确认（资料汇编） · 第 3 次确认（提纲） · 交付确认 |
| 窗口卡 · 窗口报告 | 确认卡 · 确认材料（也可以叫「阶段小结」） |
| 落章 / 盖章 · 印章 · 已落章 / 印章有效 | 确认 · 确认记录 · 已确认 |
| `stale` / 作废 / 印章失效 | 需要重新确认（确认后内容又改过） |
| 重过窗口 / 重弹 · 重渲 | 改好后再请你确认一次 · 重新生成 |
| 预告 / 执行预告 · 交付预告 | 接下来要做的事 · 交付前确认 |
| 判断三行 / 承诺三行 / 本轮承诺 | 请你重点看这三点 |
| 口径承诺 / 写作/返修期间我改了什么已批的 / 改了什么已批的 | 改动内容（这一轮改了哪些你确认过的内容；第 1 版写「这是第 1 版」，没改写「没有改动」） |

**这一步常说的几句**

- 开场第一条消息先说在哪一步、要做到什么程度：「我们在第一步：明确任务（一共四步，右侧能看到进度）。这一步要聊清楚三件事，聊完我写成一份任务计划请你确认，之后才开始找资料。」再说「先一次问完，你挑着答就行：」，下面用编号列出这个项目还没说清的问题（报告类型、研究范围、成稿形式各一问，照委托原话写具体）。例如问报告类型：「这份内参是要下一个判断（下乡活动到底有没有带动），还是先把情况梳理清楚？」问研究范围：「县里的公共充电桩包括哪些？乡镇和村里的算不算？」问成稿形式：「成稿要 Word 版、网页版，还是都要？」
- 用户答了一部分：先用一句话复述记下了什么，没答的下一条消息再一次问完。报告类型留到卡上定，弹报告类型卡之前这样说：「记下了：乡镇的桩算，村里的不算；成稿出 Word 版。还有一件请你在卡上定。」
- 报告类型卡上：成稿叫法用用户的说法（内参、报告……）；核心判断写成一句能用资料检验的话；理由里逐字引用户的一句原话，前面写「你说」。两种报告类型叫「研判型」（要对一个判断给出结论和依据）和「综述型」（梳理现状、归纳观点，不下结论）。
- 弹任务计划卡之前说一句这一版改了什么、确认之后做什么，例如：「按你的意见，时间段改成了 2021–2025 年，任务计划第 2 版写好了。确认之后我就开始找资料。」不贴路径；三点卡上有，对话里不用再说一遍。
- 用户在卡上点了确认之后：「好，任务计划按第 2 版定下了。我开始收集资料，遇到要你拿主意的事会停下来问你。」
- 用户点了「先不确认」又没写附言：「好，先不定。你想改哪里？直接说就行，只说哪一部分不对也可以。」
- 任务计划确认过之后用户说不要拟提纲：「好。已写进任务计划第 3 版：本项目跳过拟定提纲，写作按资料汇编的结构走。这改动了你确认过的任务计划，要请你再确认一次。」
- 重新确认任务计划时，如果资料汇编或提纲已经确认过，用决定卡逐份问，例如：「资料汇编已经确认过，是保留还是按新的任务计划重做？」
- 开场检查发现进度记录和文件对不上时，说「进度记录和文件对不上，我先停在这里，请你看一下。」再用一两句话说清是哪份材料；不贴检查的原始输出。
- 同一张卡连着三次没准备好：用一两句话说清卡在哪里、你打算怎么改，例如「这张确认卡上的三点我写得太长，压到字数以内再请你确认。」

## 出口契约(这一步完成的硬条件 —— 少一条就还没完成)

| # | 条件 | 怎么验 |
|---|---|---|
| E1 | `task_plan.md` 符合规格①:frontmatter(kind / version / genre / report_name / stages / scope_brief / pipeline_status / budget / evidence_standard / constraints …)+ 固定节(request / genre_rationale / thesis / definitions / scope / evidence_standard / constraints / commitments;研判型加 hypotheses / preregistration / evidence_gate)。`request` 逐字引委托原话;`thesis` 是改写过的、能用证据检验的核心判断;`genre` 与 `genre_rationale` 按报告类型卡上用户的选择写 | `pipeline_status.py` 无 FAIL;「对应表述」由 `commitments_check.py` 核 |
| E2 | 三点写在正文最后一节 `## 要你认的三件事 {#commitments}`(规格 §⑨-1),一条一行,纯文字,60 / 60 / 80 字;第 1 版的改动内容写「这是第 1 版」 | `commitments_check.py "projects/<项目名>/task_plan.md"` 退出码 0 |
| E3 | 偏离显式:证据标准、研究范围与 `toolkit/library/rules/` 默认不同处已写明;不偏离则一行「沿用默认规范：一手资料优先，来源分官方一手、机构自报、二手三类」 | 正本可见 |
| E4 | 三件事问过:报告类型(在报告类型卡上定)、研究范围、成稿形式(格式、篇幅)—— 开场一次问完,答了的随答随记进 `clarify.yaml`;任务计划里写进 `genre`、`scope` 一节与 `scope_brief`、`constraints.formats` 与 `words_max`。缺一件 = 没问完,不出任务计划卡 | 任务计划里三件事各有用户的答案 |
| E5 | 用户确认了任务计划:`--advance gate1_awaiting` → `card.py prepare task_plan` → 用户点「确认」→ `card.py answer` 写确认记录并推进到 `collecting`。你不写确认记录,也不做确认之后的推进 | `pipeline_status.py`:task_plan 已确认、状态 `collecting` |

## 出口契约附注

(E5)确认记录只能由 `card.py answer` 在用户点了「确认」之后写;你自己写出来的确认记录等于伪造批准。(E1)预算可空;超限动作 = 停下问用户,不硬停。

## 不变量(这一步任何时刻不可破 —— 红线,不是步骤)

1. **未确认不动笔** —— 任务计划没确认,不收集资料、不做资料卡片、不写稿。
2. **只有人能确认** —— 你不确认,另起的助手也不能确认;确认记录由 `card.py answer` 在用户点「确认」之后写。
3. **用户的任何话都是意见,不是确认** —— 只有卡上的「确认」算;察觉「往下走」的语气 → 主动出卡,不猜。
4. **默认值 + 偏离须声明**。
5. **三点是给复核的尺子**:①改动内容(判断、范围、口径的改动必须写明,书面修订不豁免)②最薄弱的依据(具体到哪份资料、哪个数)③最可能出错的地方(写成可以核对的预测)。三点进内容 hash;空话 = 违规。
6. **卡上只填留给你的空**:问题、选项、标签由脚本写;你填的空写实。
7. ⛔ **不给用户出题**:把材料呈现好让用户看得懂,不考他看没看。

## 变更与重新确认(按「动没动已确认的内容」分级)

**重新确认一份已经确认过的材料**(它要改,或者前面的材料重新确认之后它要跟着再确认一次)—— 三份 skill 用同一套做法:
1. `$PY "toolkit/scripts/stamp.py" "<那份材料>" --invalidate --why "<为什么>"`(旧的确认记录挪进 revision_log,它自己加一条,`v` = 当前版本加一);
2. frontmatter 的 `version` 加一,与那一条的 `v` 对齐;
3. 改要改的地方,三点的改动内容照实写 —— 内容没动就写「没有改动」(可以带一句为什么要重新确认),只改了措辞就写「只改了措辞」,改了别的就写改了什么;
4. `$PY "toolkit/scripts/stamp.py" "projects/<项目名>/task_plan.md" --advance gate1_awaiting`(任务计划)/ `gate2_awaiting`(资料汇编)/ `gate3_awaiting`(提纲),再出它的确认卡。

**只改流程**:用户说「这个不用拟提纲了」(或要把提纲加回来),任务计划已确认过,状态在 `collecting` / `gate2_awaiting`。走改流程卡(规格 §①「只改流程」):

1. 只改 `stages`(省掉提纲 = `stages: [task, sources, delivery]`;加回来 = 删掉这一行),`version` 加一,`revision_log` 加一条(`v` = 新版本,`what` 以「改流程：」开头,后面写改动环节那一句)。别的一个字都不动 —— 三点也不动。**不作废确认记录,不推进状态。**
2. 发一句话说改了什么、要请用户再确认一次,然后把卡上的空写进 `projects/_inbox/<项目名>/fields.json`,按 `yunzhi-card` 出卡:`$PY "agent-tools/card.py" prepare flow_change "<项目名>" --fields-file "projects/_inbox/<项目名>/fields.json"`

```json
{"kind": "flow_change", "changes": "去掉拟定提纲这一步，写作按资料汇编的结构走。"}
```

   `changes` ≤60 字:去掉或加回了哪一步、写作按什么结构走。卡上「判断、范围、口径都没动」和改完之后的步骤由脚本写;脚本会拿这一版和上次确认的那一版比,多动了别处就不出卡。
3. 用户点「确认」→ `card.py answer` 写确认记录,状态不动,接着干原来的活。只写了意见、没说清（例如「直接帮我确认吧」）→ 先别还原，照 `next` 说 `say`，等用户回 1 或 2（不用重新出卡）。点「先不确认」（或者意见里明说还要原来的步骤）→ 照 `card.py answer` 的 `next` 把 `stages` 和 `version` 改回原值、`revision_log` 再加一条(`v` 仍写刚才那个没被确认的版本号,不许更大);原来的确认照旧有效,按原流程走。
4. 任务计划还没确认过:直接改 `stages`,随任务计划卡一起确认。已经进了拟定提纲(`outlining` 及以后)再说不要提纲:这一版不支持中途去掉 —— 用决定卡和用户商量(把提纲压到最简、一轮就确认,还是照常做)。
5. 改流程卡等用户的时候你被重启了:`projects.py status` 会报 `consistent: false`、`flow_change_pending: true` —— 这是预期的,别停下:用同一个命令再出一次改流程卡(卡号不变)。

**改了流程以外的内容**(判断、范围、口径、报告类型……;包括用户在决定卡上选了会改任务计划的那一项):

1. 任务计划照上面「重新确认一份已经确认过的材料」改、再请用户确认(推进到 `gate1_awaiting`);三点的改动内容写明改了哪些已确认的内容。
2. **后面的材料怎么办(必做)**:资料汇编、提纲若已确认过 —— 它们是按旧任务计划写的,确认记录不会自动失效 —— 先用决定卡逐份问用户保留还是重做,不许默认保留:

```json
{"kind": "decision", "question": "资料汇编已经确认过，是保留还是按新的任务计划重做？", "why": "任务计划改了研究范围，资料汇编是按原来的范围收集的。不先定下来，就不知道要不要回头补资料。", "options": [{"label": "保留资料汇编", "effect": "不重新收集，写作时只用和新范围相符的部分。", "changes_plan": false}, {"label": "按新的任务计划重做", "effect": "回到收集资料，补齐新范围的资料后再请你确认。", "changes_plan": false}]}
```

   决定卡怎么出见 evidence-card「中途要用户拿主意」。
3. 出任务计划卡(第 4 步的 3–7 小步)。用户确认后 `card.py answer` 把状态推进到收集资料;之后资料汇编、提纲按顺序各照「重新确认一份已经确认过的材料」再确认一次 —— 选了重做的那份先重做,保留的那份内容不动、改动内容写「没有改动」。
