# yunzhi-card · 选项卡

> 命令规矩见 AGENTS.md 第一节（`$PY`、在工作区根目录下跑、路径加双引号、交给脚本的文字先用写文件的工具写进文件）。下面的 `<项目名>` 换成 `projects/` 下那个项目文件夹的名字。

每张卡都是三步，**一步都不能省**：①准备（prepare）→ ②发出来 → ③收回答（answer）。

## 第 1 步 准备：跑 prepare

```
$PY "agent-tools/card.py" prepare <kind> "<项目名>" [--fields-file "projects/_inbox/<项目名>/fields.json"] [--outside none] [--pane-open]
```

**kind 和要你填的空**（规格 §⑦；字数是上限，按字符数算，标点、数字、空格各算一个）：

| kind | 什么时候 | 要你填的空（写进 `projects/_inbox/<项目名>/fields.json`） | 还要带 |
|---|---|---|---|
| `report_type` | 明确任务，写任务计划之前 | `report_name` ≤6 · `thesis` ≤40 · `why` ≤80（必须用「」逐字引用户的一句原话，前面写「你说」）· `recommend`：`judge` 或 `survey`，不推荐就不写 | |
| `task_plan` | 任务计划写好或改好，进度已推进到 gate1_awaiting | 不用填 | `--outside` |
| `dossier` | 资料汇编写好，进度已推进到 gate2_awaiting | 一般不用填；研判型的反向检索找到的卡里有没归为不支持的（脚本会说是哪几张），重核归类之后给每一张写一句为什么：`counter_reasons`：`{卡号: 理由 ≤40}`（卡上逐条显示「标题 → 归为背景资料：理由」） | `--outside` |
| `outline` | 提纲写好或改好（第 1 版写好就出），进度已推进到 gate3_awaiting | 不用填 | |
| `delivery` | 交付前检查全过、复核结果对得上当前成稿且必须改为 0、交付的三点写好，进度在 verifying | 不用填 | |
| `decision` | 做到一半要用户拿主意 | `question` ≤40（一个选择，问号结尾）· `why` ≤80（卡在哪里、不问会怎样）· `options` 2–3 个，每个 `{label ≤20, effect ≤40, changes_plan 真或假}` · `recommend`：从 1 数的选项序号，不推荐就不写 | |
| `flow_change` | 任务计划确认过，只改了流程（去掉或加回拟定提纲） | `changes` ≤60（去掉或加回了哪一步、写作按什么结构走） | |
| `pick_project` | 有几个项目，请用户选一个（不带项目名） | 不用填 | |

- 不用填空的卡，不写 `--fields-file`。`fields.json` 写在 `projects/_inbox/<项目名>/` 下面（每个项目自己一个文件夹，几个对话同时干活不会互相覆盖）。
- `--pane-open`：**这个对话里已经把右侧挂上了**（照 `yunzhi-progress` 第 1 节调过一次）才带，所有确认类的卡都带；没挂过（命令行、WorkBuddy 没有右侧）就不带。卡上的「右侧已打开」只有带了它才写，不然用户会去找一个不存在的右侧。
- `--outside`：这一轮你读过的**项目以外**的文件，一个路径写一次 `--outside "<路径>"`；一个都没读过就写 `--outside none`。工作区里的 `toolkit/`、`wording/`、skills 不算；`~/.codex/` 下的记忆、别的插件或 skill 的说明文件、用户电脑上别处的文件都算。卡上只写文件的名字（注明「助手自报」），照实报。
- 决定卡的选项名：每个选项写不同的做法；不能写「跳过」，不能只写一个数字，也不能以「数字 + 标点」开头（用户回「2，……」是在选第 2 项），别自己写「 · 助手建议」（推荐哪项用 `recommend`）。
- **推荐的那一项排第一**：报告类型卡、决定卡上有推荐的，脚本把它挪到第一个（原生卡默认选中第一项），卡上的编号跟着变。你在 `fields.json` 里照自己的顺序写就行；answer 交回的 `selected` 还是按你写的顺序数。确认类的卡「确认」总在第一。
- 卡号由脚本定（`task-plan-v2`、`dossier-v1`、`delivery-1`……），写在输出的 `card_id` 里。

**看输出**：
- `ok` 为 true：卡准备好了，做第 2 步。
- `ok` 为 false：卡没出。照 `refuse`（和 `problems` 里的每一条）改 —— 改材料，或改 `fields.json` 里的空 —— 再跑同一条 prepare。不要跳过检查、不要换个说法绕过去。输出里有 `tell_user` 时（连着三次没准备好），把 `say` 那句告诉用户，再用一句研究上的话说你打算怎么改。

## 第 2 步 发出来

**材料已经在右侧**：确认类的卡（任务计划、资料汇编、提纲、交付、改流程），prepare 已经把那份材料生成了好读的网页，并换进了右侧那一页（等于跑了 `view.py --pane`；输出里有 `pane_url`，右侧自己会刷新出来，通常几秒，最多半分钟）。你**不用**做任何事，也**不要**为了换页面去打开右侧。带了 `--pane-open` 的卡，「依据的材料」那一行写着「右侧已打开」；原生选项卡的消息里附了点开看的链接（`view_url`，指向那份材料自己的网页），文字卡上写的是材料在项目文件夹的哪里（不放网址）。右侧还没挂过（这个对话里第一次碰这个项目），照 `yunzhi-progress` 第 1 节挂一次，之后的卡都带 `--pane-open`。

**发卡**，看输出里的 `mode`：

- **`native`（原生选项卡）**：
  1. 把输出里的 `message` **原样**作为一条消息发出（抬头、依据的材料、三点都排好了，最后一句提醒卡片两三分钟没操作会自动收起）。不要改字、不要加你自己的数字。这一步不能省：确认卡的问题里虽然也带了三点的紧凑版，卡前这条消息才是完整的材料。
  2. 马上调平台的选项框工具，参数用输出里的 `ask`，**一个字都不改**（尤其是 `id`：`dossier-v1` 不能写成 `dossier_v1`；守门脚本在跑时，参数和 `ask` 不一致会被拦下，见 AGENTS.md 第九节）：Codex 调 `request_user_input` —— **只用这个会等回答的**，不用 `request_user_input_async`（它不等用户回答就往下走，回答后来作为一条新消息进来，和卡对不上）；WorkBuddy 调 `AskUserQuestion`（问题、选项名、选项说明照 `ask` 填）。
  3. 没有选项框工具，或调用报错 → **重新跑同一条 prepare，加 `--mode text`**，发它输出的 `fallback_text`，然后结束这一轮，把用户的下一条消息当作回答。
     - 只有这两种情况才改用文字卡：工具列表里根本没有 `request_user_input`，或者你真的调了、调用返回了错误。用户上一张卡是手写回答的、这个对话里已经弹过卡、担心卡片会被自动收起，都**不是**改用文字卡的理由：照样先调 `request_user_input`（第五轮桌面复测：助手准备好原生卡后没调工具，就自己改成了文字卡）。
- **`text`（文字卡模式）**：把输出里的 `fallback_text` 原样发出，**不调选项框工具**，结束这一轮；用户的下一条消息就是回答。

发出卡之后、用户回答之前：不改那份材料和它依据的东西、不推进进度、不出别的卡。

## 第 3 步 收回答：马上跑 answer

**硬规矩（第三轮、第四轮都实测到：助手先说了「已定下」，脚本却认不出那个回答，或者用户点的根本不是确认）**：拿到回答（工具返回，或者文字卡模式下用户的下一条消息），这一轮的第一件事就是下面第 1、2 小步：写回答文件、跑 answer。**在 `answer` 跑完之前，不对用户说结果**：要么什么都不说，要么最多说一句中性的「收到，我记一下。」；任何结果都不许说 —— 「好，已定下」「确认了」「好，按你的意见改」「那就先不交付」都不行。结果只照 answer 的输出说：有 `say` 就原样说 `say`。

1. 用写文件的工具把回答**原文**写进 `projects/_inbox/<项目名>/answer.txt`（选项目的卡写 `projects/_inbox/选项目/answer.txt`）：
   - 原生选项卡：工具返回的那段原文，一字不改，例如 `{"answers":{"task-plan-v2":{"answers":["确认，开始收集资料"]}}}`；用户在卡上写了一段话时，字符串就是那段话，例如 `{"answers":{"report-type":{"answers":["2，另外把各地进展的差距也写进去"]}}}`；点了跳过（或者两三分钟没操作被自动收起）时是 `{"answers":{}}`。都照写。
   - 文字卡：用户回的那条消息，一字不改（可能是一个数字、一个选项名、数字后面接一句意见，或者一段意见）。
   - 守门脚本在跑时（AGENTS.md 第九节），answer 会拿它记下的用户原话、卡上交回的原文核对：对不上就退回（`ok` 为 false，这张卡照旧开着），照退回的话把原文重写一遍再跑；用户还没回答，就等他回答。
2. 跑：

```
$PY "agent-tools/card.py" answer "<项目名>" --card <card_id> --answer-file "projects/_inbox/<项目名>/answer.txt"
```

3. 照输出的 `next` 做；有 `say` 就把那句话原样说给用户。answer 已经把右侧换回进度页（等于跑了 `progress.py --page --pane`），不用你再调任何工具。`result` 的意思：

| result | 意思 | 你做什么 |
|---|---|---|
| `approved` | 用户选了确认 / 交付（点了，或者回了 1）；确认记录已经写好，进度已经推进（附了意见的，意见记进了确认记录，`next` 里写着照做） | 说 `say` 里那句，照 `next` 交接到下一步 |
| `not_approved` | 用户选了「先不确认」（点了，或者回了 2），或者只写了意见、没选选项（只写意见 = 先不确认）；什么记录都没写 | 选了「先不确认」：说 `say` 里那句，照 `next` 改材料。只写了意见：照 `next` 二选一 —— 意见里说了要改什么，说 `say_revise` 里那句、照改、出新版的卡；没说要改什么（有 `looks_like_yes` 时也是），不改材料，说 `say` 里那句（里面告诉用户回 1 就能定），停下等用户（见下面「只写了意见之后」） |
| `selected` | 报告类型卡、决定卡、选项目卡选了一项（可能还附了意见） | 说 `say` 里那句，照 `next` 做 |
| `note` | 报告类型卡、决定卡上没选选项、只写了意见 | 照 `next` 二选一：意见是要改卡上的内容，说 `say_revise` 里那句、改好重新出卡；其余先用一句研究上的话回应意见，再说 `say` 里那句（列着选项的编号），停下等用户（见下面「只写了意见之后」） |
| `skipped` | 卡收起来了：用户点了「跳过」，或者太久没操作被自动收起（文字卡回了「跳过」）| 说 `say` 里那句（里面列着选项的编号），停下等用户；不确认、不推进 |
| `unclear` | 认不出回答的样子（原文已经存下，**这张卡关了**） | 说 `say` 里那句，问清用户选了哪一项，再重新 prepare 出卡；**不许猜，也不许当成选了推荐的那项** |
| `changed` | 用户看卡期间材料或它依据的东西变了，或者这件事已经定过了；没写确认记录 | 说 `say` 里那句；要再问就重新出卡 |
| `error` | 写确认记录或推进失败 | 说 `say` 里那句，等用户定（不写进任何材料） |

**用户怎么回都认**（文字卡和原生卡一样，脚本认，你照原文写进回答文件就行）：选项前面的数字（「1」「选 2」「第 2 个」）、选项名；数字或选项名后面隔着标点或空格接一句话（「1，判断标准里要把透支效应算进去」「先不确认，时间段再看看」），就是选这一项再附一句意见。数字后面紧跟数字（「2023 年的数据也要」）、数字不在开头（「我选 1 吧」）都只算意见。

**卡收起来之后**：用户之后回的消息，照 AGENTS.md 第三节第 6 条先记用户消息；`note-user` 的输出里有 `looks_like_answer` 时，这条消息就是那张收起的卡的回答 —— 照它的 `next` 把消息原样写进回答文件、跑 answer，**不用重新出卡**（一张卡收起来之后只能这样再回答一次，而且这期间没出过别的卡）。没有 `looks_like_answer` 就照常当对话回应。用户说「确认任务计划」这类话要你把卡拿回来，就重新跑 prepare 出这张卡。

**只写了意见之后**：用户在卡上（或文字卡回的消息里）只写了一段话、没选选项 —— 确认类的卡记成先不确认、报告类型卡和决定卡记成 `note`，什么记录都没写。意见里没说要改什么（例如「直接帮我确认吧」「这版可以」），你不改材料、说 `say`，停下等用户；用户下一条回的是数字或选项名（例如「1」「1，其余都可以」），记用户消息时 `note-user` 的输出里会有 `looks_like_answer` —— 照它的 `next` 把消息原样写进回答文件、跑 answer，**不用重新出卡**。条件和卡收起来之后一样：只此一次；这期间没出过别的卡；确认类的那份材料没改过（你照意见改了材料，这张卡就作废了，照常出新版的卡）；守门脚本在跑时，只认用户在那之后说的原话。

每张卡只能回答一次，只有收起来之后、只写了意见之后可以再回答一次：回答过的卡（包括 `unclear`、`changed`、`error`，也包括明明白白选了「先不确认」的）就关了，要再问用户，重新跑 prepare。

## 规矩

1. 一个决定一张卡；一张卡只问一件事。只是要用户补一句话的普通问题（这家机构的全称是什么），不出卡，直接在对话里问。
2. **确认记录只能由 `card.py answer` 写。**用户在对话里说「可以」「没问题」都不是确认 —— 出卡请他选。
3. 你填的空里，「」只放用户的原话（一字不差，脚本会拿委托原话和用户消息记录核对）；你自己的话不加「」。唯一的例外是报告类型卡的问题：「这份内参是要对「…」下一个明确判断」里的「」是卡片模板自己的格式，装的是你写的核心判断，不算引用用户。
4. 卡上提到助手一律是「助手」（脚本写的固定文字都这样），你填的空里也别写「我」。
5. `fields.json` 和 `answer.txt` 每次都重新写，放在 `projects/_inbox/<项目名>/` 下面；脚本读完就删。
6. 文字卡模式由用户或测试的人打开：环境变量 `YUNZHI_CARDS=text`，或在 `projects/` 下（或某个项目文件夹里）放一个名叫 `.text-cards` 的空文件。你不用自己开关它；看 prepare 输出的 `mode` 就行。选项框工具用不了时用 `--mode text` 重新准备，见第 2 步。
7. **上下文被压缩过（compaction）之后，出下一张卡之前先把这份说明重读一遍**（第三轮实测：压缩之后没重读，交付卡前那条消息没发，用户没看到三点和检查结果就点了交付）。同一个对话里没压缩过，就不用反复重读。
8. 对话里的进度快照这一版停用：answer 不加 `--snapshot-dir`，回复里不放 `visualize{…}` 那一行（见 AGENTS.md 第五节）。

## 对用户说话

- 卡前那条消息就是 `message`（或 `fallback_text`），原样发，不另加解释、不加数字。
- 出卡前可以先说一句为什么出这张卡，用研究上的理由说，例如「任务计划第 2 版写好了，右侧是全文，请你看一下。」不贴路径、不复述三点（卡上有），不提这份说明。
- 卡收起来了：照 `say` 说，例如「这张卡先收起来了（你点了跳过，或者太久没操作被自动收起）。想好了直接回复选项前面的数字就行。」
- 只写了意见、没选选项：照 `say` 说，例如「任务计划第 2 版还没定下来：你写的话算意见，不算确认。要按这一版定下来，直接回 1 就行；要改的话告诉我改哪里。」（意见里说了要改什么、你照着改的时候，说 `say_revise`）。最后那句「怎么继续」一定要说，不要省。
- 回答认不出：照 `say` 说，例如「我没看清你在卡上选的是哪一项，能再说一下吗？」
