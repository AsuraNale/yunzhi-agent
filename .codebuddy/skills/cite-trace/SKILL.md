# cite-trace · 第四步：撰写交付

> 命令规矩见 AGENTS.md 第一节（`$PY`、在工作区根目录下跑、路径加双引号）。`<项目名>` 换成项目文件夹的名字，`<稿>` 换成成稿的文件名（一般就用项目名）。前提：本项目流程里的材料（任务计划、资料汇编、提纲）都已确认。公理：**先卡后文** —— 写作期只用已有的资料卡片与参考文献清单，不引入新材料。

## 你在哪

最后一步。完成 = 用户在交付卡上点了「交付」+ 归档做完。用户随时可以看草稿、提意见 —— 改底稿、重新生成是免费的。**两种格式都生成**（网页版与 Word 版）；任务计划 `constraints.formats` 记的是用户要拿到哪种，交付时告诉他那一种在项目文件夹的哪里（成稿那个文件夹）。**篇幅按任务计划（第一步问过的，别再问）。**

写作中发现缺资料 → 停：回 evidence-card 补资料（资料汇编作废、重新确认），不许临场编、不许「先写完再补」。要大改提纲结构 → 先用决定卡问用户，再回 outline-cocreate。

## 这一步怎么走

### 第 1 步 写底稿

用写文件的工具写 `projects/<项目名>/drafts/<稿>.md`：第一行 `# <成稿标题>`；按提纲的节写（`##` 一级节、`###` 小节）；正文引用一律写占位 `[[R001]]`（参考文献清单里的 id），不写网址、不写「见某张资料卡片」。每个实质数字都从资料卡片的 `facts` 里抄（带口径），不凭记忆。

### 第 2 步 链接探测（交付前必做，放在复核之前）

```
$PY "agent-tools/liveness.py" "<项目名>"
```

它给参考文献清单的每一条记下链接还能不能打开（五态）。输出里 `offline` 为 true（一条都连不上：这个环境不能联网，桌面版常常这样）时，脚本把每条记成「未能自动检查」，不算链接坏了；这时：

- 这一轮你用网页工具**亲手打开、读过**的页面，记成能打开（带日期）：`$PY "agent-tools/liveness.py" mark "<项目名>" --id R001 --id R002`（编号是参考文献清单里的 id）。没打开过的不许记。
- 把输出里的 `say` 告诉用户（「这次未能自动检查链接还能不能打开……」），不要说链接「失败」。

输出里有 `retry`：这几个来源当初没读到（资料卡片上记的是打不开或出错），现在链接打得开了。**写进成稿之前，先用网页工具真的打开读一遍**：读到了，就照 `next` 记下重新取到了（`fetches.py add … --state ok`）、改资料卡片（`fetch_state: ok`、原文摘录、查阅日期）、再跑 `refs_add.py`；还是读不到，就照旧，不引用它。参考文献里没读到过的来源，成稿上会写「未能打开」，不写「查阅于」。

输出里有 `gap_sources_reachable`：资料缺口卡上当初没读到的来源，现在链接打得开了 —— 这几个缺口当初就是因为它们没读到才立的，现在可能补得上（第九轮实测：主缺口那张卡上的来源重新打得开，助手没再读）。**先用网页工具把它们真的重读一遍，再定缺口**：读到了要的数据，照 `next` 记下重新取到了、另做一张资料卡片（旧卡不改）、把资料汇编里这个缺口照实改掉，资料汇编要请用户重新确认；还是没有要的数据，缺口照旧。

输出里有 `cited_unreached`：成稿里引用了、链接探测却没打开（打不开、连不上）的来源。交付前检查会拦它们（第八轮实测：一条引用了两次的来源探测连不上，其实你和复核助手都读过它，记录却一直写着打不开）：
- 资料卡片上有它的原文摘录（`read` 为 true，这就是读过的证据）：跑 `next` 里那条 `liveness.py mark` 记下读过。这几种不上 ⚠，成稿一个字不变，**不用重新生成**。
- 没有读过的证据（`read` 为 false）：mark 会拒 —— 没读过的不能记成读过。用网页工具真的读一遍，读到了照资料卡片的做法补上原文摘录再记；读不到就改掉成稿里引用它的地方。

### 第 3 步 生成两种成稿，推进到交付前检查

```
$PY "toolkit/scripts/render_html.py" "projects/<项目名>/drafts/<稿>.md" "projects/<项目名>/references.yaml" "projects/<项目名>/out/<稿>.html" --title "<成稿标题>" --cards "projects/<项目名>/cards"
$PY "toolkit/scripts/render_docx.py" "projects/<项目名>/drafts/<稿>.md" "projects/<项目名>/references.yaml" "projects/<项目名>/out/<稿>.docx" --title "<成稿标题>"
$PY "toolkit/scripts/stamp.py" "projects/<项目名>/task_plan.md" --advance verifying
```

- `--advance` 只对任务计划跑（进度只记在那里），别的文件一律不跑。

- 两种成稿由同一份底稿生成，禁止手改任何一份成稿；要改就改底稿再重新生成。
- `render_html.py` 打印的「文内引用 N 处 · 参考 N 条 · 章节 N · 表格 N」是机器数的，对用户说这些数时照它写。

### 第 4 步 交付前检查，修到全过

```
$PY "toolkit/scripts/cite_check.py" --project "projects/<项目名>"
```

- 退出码 0 = 全过。有 `[FAIL]`：照每条后面的修复提示改（回底稿、资料卡片或参考文献清单改），改了底稿就回第 3 步重新生成，再跑这一步。
- 预算那一项报步数没取到、出处字段缺，是提醒，不是要处理的问题（这一版取不到步数）。

### 第 5 步 独立复核（另起一个**不带对话**的助手，第 n 轮，n 从 1 起）

复核的价值在「外人眼」：复核助手**不许看到写作过程**（第三轮实测：三次复核都带着整段写作对话，等于自己核自己，上下文还撑到要压缩）。

1. 开始这一轮：

```
$PY "agent-tools/review.py" start "<项目名>" --round <n>
```

   它记下这一轮复核的成稿、写好给复核助手的说明（只列它该读的文件、成稿逐段编号、要交的东西），输出里有：
   - `spawn.message`：起复核助手的那条消息，**一字不改**照用；
   - `code_notice`：一个「复核暗号」。它只是给你看的：**不许写进给复核助手的消息，也不许写进任何文件**。复核助手要报告它在说明之前见过的暗号 —— 带着对话起的复核助手看得见它，封存时就会被拒绝。
2. 另起复核助手：
   - **Codex**：调协作工具 `spawn_agent`，参数照输出里的 `spawn`：消息就是 `spawn.message` 那一句（原样），**`fork_turns` 明写 `"none"`** —— 这一项不写，Codex 默认是 `"all"`，会把整段写作对话分给复核助手，这一轮就不算独立；绝不写 `"all"`，也不写轮数。然后用 `wait_agent` 等它做完。别自己打开那份说明（里面的随机码只给复核助手）。**起了之后不再给它发消息**（不用 `send_message`、`followup_task`，也不打断它）：它只看那份说明，你只管等它交卷（守门脚本在跑时会拦）。**等的时候在对话里说一句就够**，例如「一个没参与写作的助手正在独立复核，做完我告诉你结果。」然后就等它交卷，不要每隔一会儿再发一条「还在等」（第九轮实测：连发了约 7 条）。
   - **WorkBuddy**：调用 `review-module` 这份 skill（它开头写了 `context: fork`），把 `spawn.message` 那一句交给它。
3. 复核助手做完会自己跑 `review.py seal` 封存（它先核复核助手交的那份 inputs 文件：没见过暗号、逐段核了、抽核了资料卡片和原文；过了才封存）。封存被拒、或复核助手报它见过暗号 → 这一轮不算：`$PY "agent-tools/review.py" abandon "<项目名>" --round <n>`，再从第 1 小步起开 n+1 轮，重新起一个**不带对话**的复核助手。复核进行期间别动成稿：动了也是同样处理。
4. 看结果：`$PY "agent-tools/review.py" check "<项目名>"`。退出码 0 = 复核结果对得上当前成稿、必须改 0 处、而且是这样封存的，去第 6 步。不是 0：
   - 必须改的全改；说法要收一收、引用或格式损坏的也改。改底稿 → 回第 3 步重新生成 → 第 4 步检查 → 再复核一轮（n 加一；复核助手会把上一轮还开着的发现照抄过来核改好没有）。
   - **复核封存之后成稿一个字节也不能再动**：动了（哪怕重新生成一次）就对不上，要再复核一轮。所以链接探测、最后一次生成都放在复核之前。

### 第 6 步 交付的三点

用写文件的工具写 `projects/<项目名>/library/delivery_commitments.md`（整个文件就是三点；不写锚点、不写 frontmatter）：

```markdown
# 交付 · 要你认的三件事

1. **改动内容**：第四节标题按你的意见改了；没有改动任何判断。
2. **最薄弱的依据**：第三节参加县增速 41% 只来自 3 个地市的数据。
3. **最可能出错的地方**：2025 年数据只到三季度，全年数字公布后可能变化。
```

- 第 1 条写写作和返修期间改了哪些用户确认过的内容（判断、口径、范围、提纲结构），没有就照实写；第 2 条是成稿里最站不住的一处；第 3 条是最可能出错的地方。一条一行，60 / 60 / 80 字。三点只写成稿本身的事：脚本出错、工具报错不写进来，在对话里说。
- 自查：`$PY "toolkit/scripts/commitments_check.py" "projects/<项目名>/library/delivery_commitments.md" --delivery` 退出码 0。

### 第 7 步 出交付卡

1. 发一句话：成稿写完了、交付前检查和复核都过了，请用户看交付卡。成稿有几节、几处文内引用、几条参考文献，交付前检查和复核的结果，脚本都从文件里数好、排进了卡前那条消息，你不用自己报数。
2. 按 `yunzhi-card` 出卡：`$PY "agent-tools/card.py" prepare delivery "<项目名>"`。prepare 会顺手把成稿的网页版换到右侧给用户看（见 `yunzhi-card` 第 2 步），不用你另外打开。脚本出卡前自己再跑一遍交付前检查、读复核结果、核交付的三点：没全过、复核对不上当前成稿、还有必须改的，它不出卡，照它说的补齐，不要绕。
3. 收回答，照 `card.py answer` 的输出：
   - `approved` → 已推进到已交付，交付记录写好了，归档也由脚本做了（输出里 `archived.ok` 为 true；归档用的是 `agent-tools/archive.py`）。说 `say` 里那句话。`archived.ok` 不是 true：照 `archived.problems` 改好，跑 `$PY "agent-tools/archive.py" "<项目名>"`，再跑 `$PY "agent-tools/archive.py" "<项目名>" --check` 到退出码 0（自己改，不用问用户）。**不自己写归档的脚本**，项目文件夹里也不放任何脚本。
   - `not_approved`（先不交付，或写了意见）→ 照意见改（没写意见就问改哪里），改完从第 3 步重来，交付的三点按这一轮的改动重写。只写了意见、没说要改什么：照 `next` 不改成稿，说 `say`，等用户回 1（不用重新出卡）。

## 对用户说话

> 用户是政策、公共事务、产业经济方向的研究员，不是开发者。本节管你**对用户说出口的每一句话**：普通消息、对话里的提问、进度汇报、阶段交接，卡上留给你填的空，以及给用户看的材料里你自己写的句子。
>
> 本 skill 其余部分用的是内部叫法（文件名、字段名、状态名、脚本名）。干活、写文件、跑命令时照旧用；**说给用户时换成下面词表的右栏**。确认卡、决定卡上的问题、按钮和标签由出卡脚本写，你只填卡上留给你的空，填的空同样按本节写。

**五条原则**

1. 不出现英文内部词、编号和文件名：argument、E4、task_plan.md、hash 这类。需要指代某个东西时，用它的研究员名称加版本，例如「任务计划第 2 版」。
2. 每个内部对象只用一个研究员名称：任务计划、资料汇编、提纲、成稿、资料卡片、参考文献清单。不要一会儿叫正本、一会儿叫 dossier。
3. 流程动作说成「确认 / 修改 / 重新确认」，不说落章、作废、重弹、推进 collecting。
4. 检查结果只说「有什么事需要你知道或决定」，不报检查项名，也不报 PASS/FAIL。
5. 方法论的动作说成它对报告的影响。例如不说「预注册」，说「先把几种可能的结论和判定标准写下来，结论就不会随着证据被挪」。

**引用怎么写**：用户的原话逐字照抄，放进「」或整段放进 `>` 引用块，前面写明这是「你的原话」或「委托原文」；文献和报告的标题放进《》。出卡脚本会扫一遍用词，并把卡上「」里的字和用户写过的话（委托原话、用户发过的消息）逐字核对：对不上的不算引用，照样算你的用词。所以卡上填的空里，「」只放用户原话；你自己的话（包括环节名、章节名）不加引号。

**研究流程的四个环节**：明确任务 · 收集资料 · 拟定提纲 · 撰写交付。确认点：第 1 次确认（任务计划） · 第 2 次确认（资料汇编） · 第 3 次确认（提纲） · 交付确认。

| `PASS` · `WARN` · `FAIL` | 通过 · 提醒 · 必须处理 |
| `cite_check` / `card_check` / `dossier_check` / `outline_check` / `pipeline_status` / `stamp.py` / `render_*` · 十二项全绿 / 全绿 | 自动检查 · 交付前的自动检查全部通过 |
| 检查器 / 检查脚本 · 机器取值 | 自动检查 · 自动统计的数 |

**不要对用户提**：出口条件的编号（E 加数字）、引文占位符 [[R###]]、`frontmatter`、`commitments`、`PROGRESS`、`hash`、元信息条、工具包、`uid`、`stance`、`evidence_mode`、五态、聚合、招式、式①这类招式编号、子代理、会话日志、`steps`、步数、`py`、`pwsh`、`PATH`、127.0.0.1、`skill`、`DSH`、公理。需要时换成上表的说法，或者干脆不说。

**研究员本来就懂、可以直接用**：口径（只用统计口径、数据口径的本义；「口径承诺」「项目口径」「口径放宽」要改写）、综述（不说 survey）、假设（不用 H1/H2 这类编号）、反例 / 边界案例、缺口（不带 gap 和状态码）、转引、复核、红线（不带编号，每条用一句大白话说）、判定标准、一手资料 / 二手资料、截至（数据截至某日）、概念界定、提纲 / 大纲、成稿、确认。

**这一步常说的几句**

- 开场这样说：「最后一步：撰写交付。按确认过的提纲写成稿，交付之前会做自动检查和一轮独立复核。」
- 自动检查的结果只说需要用户知道或决定的事，例如「有 3 个数字还没找到出处，我正在补」；你自己能修的先修好再说。全部通过时说「交付前的自动检查全部通过」。
- 转述复核发现时，严重程度说成：必须改 / 说法要收一收 / 引用或格式损坏 / 抽查无误；「八类曲解」说成「八类改写失真」。
- 写作中发现缺资料时这样说：「写到这里发现还缺资料，需要回去补；补完资料汇编要请你重新确认一次，然后接着写。」
- 弹交付卡之前，一句话说成稿写完了、请他看卡；节数、引用、参考文献和检查、复核的结果脚本已经排在卡前那条消息里，你不用自己报数，例如：「成稿写完了，交付前检查全部通过，一个没参与写作的助手也复核过了。请你看看能不能交付。」
- 用户点了「先不交付，回去改」又没写附言：「好，先不交付。你想改哪里？」
- 交付之后这样说：「成稿已交付。这次用到的来源和还没补上的资料缺口已经存档，留给以后的课题。」

## 出口契约附注

**说给用户的数字从哪来**:章数、字数、引用、参考文献、资料卡片张数一律照脚本输出(生成时打印的那一行、交付前检查、`projects.py count`),不许自己数。「文内引用」只能抄生成时打印的数,不是交付前检查第 ③ 项的数(那个数的是去重后的外链)。每个数字都要知道量自哪个格式:量过网页版不等于量过 Word 版。

**复核结果绑的是成稿的字节**:复核之后改一个字、重新生成一次(Word 版文件里带生成时刻,字节就变了),结果就对不上,交付卡出不来 —— 要再复核一轮。

## 写作纪律(干到哪条守哪条)

- 正文引用一律写占位 `[[R###]]`(生成时按出现顺序编号);禁止裸网址;禁止「见资料卡片 X」当终点引用;引用证据弱的卡、资料缺口卡之前必须回源重验,验不过就别引。
- 每个实质数字都必须能回溯到某张卡的 facts(带口径)或参考文献清单的条目 —— 写的时候就从卡里抄,交付前检查第 ⑤ 项会逐个扫。
- 按提纲写:point / task 是要求,evidence 是能用的资料范围;超出 evidence 的论断 = 越过资料能支持的范围。
- 机器只抓得到链接层的改动,纯文字层的改动抓不到 —— 靠纪律与独立复核,不是「反正会被拦」。
- 交付三点的改动内容写写作和返修期间改了哪些确认过的内容;升版靠这条纪律,机器不拦。
