# outline-cocreate · 第三步：拟定提纲

> 命令规矩见 AGENTS.md 第一节（`$PY`、在工作区根目录下跑、路径加双引号）。`<项目名>` 换成项目文件夹的名字。字段与格式见 `toolkit/04-正本规格-v1.md` §④。前提：任务计划与资料汇编都已确认；方法论内容（判定标准、中途检查点）引用任务计划，不重复写。

## 你在哪

第三步。完成 = 提纲在确认卡上被用户确认。**第一版写好就出提纲卡**：用户在卡上写的意见（直接写，或者回「2，……」）就是共创的一轮 —— 你照意见改一版，再出卡，直到用户选确认（第五轮：先在对话里来回问「还有没有要动的」再出卡，常见情况多一个来回，也显得程序化）。

## 这一步怎么走 —— 写一版、出卡、按卡上的意见改

用户在对话里先给了想法（口述结构、点名要哪几节），照着写进第一版；没给就你先拟。

### A. 写提纲（第 1 版）

先跑 `$PY "agent-tools/projects.py" now` 拿到现在的时刻，再用写文件的工具写 `projects/<项目名>/outline.md`，照这个样子（节点块的写法很严格：标题行末尾 `{id: …, words: …}`，下面四行 `- point:` `- task:` `- evidence:` 和可选的 `- evidence_mode:` `- revision:`）：

````markdown
---
kind: outline
version: 1
updated_at: '<现在>'
genre: argument
task_plan_ref: task_plan.md#v2
total_words: 8000
tolerance: 0.1
revision_log: []
---

# 提纲

## 一、问题与判断 {id: s1, words: 800}
- point: 这一节要说的判断，一句
- task: 这一节要做的事
- evidence: [S02, S10]

## 二、县域充电设施是怎么变的 {id: s2, words: 1800}
- point: ……
- task: ……
- evidence: [S01, S03, S05]

### 2.1 增速对比 {id: s2-1, words: 1000}
- point: ……
- task: ……
- evidence: [S02, S12]

## 五、政策建议 {id: s5, words: 1600}
- point: ……
- task: 提三到五条建议
- evidence: []
- evidence_mode: synthesis

## 要你认的三件事 {#commitments}

1. **改动内容**：这是第 1 版。
2. **最薄弱的依据**：……
3. **最可能出错的地方**：……
````

- 节点 `id` 唯一、永不复用；`evidence` 只写已有的资料卡片卡号（先有卡再绑）。
- `evidence` 为空的节必须写 `evidence_mode`：`methodology`（方法说明）、`synthesis`（综合 / 收束）或 `pending_evidence`（资料待补）。综述型每节 `evidence` 都不能空（综合 / 收束节写 `synthesis`）。
- 一节写了 `words`，就是它连同下面小节的总数；`total_words` 写任务计划里的目标字数。
- 修订说明一律写 `revision` 字段（新增 / 深化 / 拆分 / 合并），不许混进 `evidence`。
- 三点放在所有节点之后，一条一行，60 / 60 / 80 字。改动内容里，措辞强度词（从来 / 唯一 / 独有）的改动别漏。
- 写完第 1 版，直接做 B（自查、出卡），不用先在对话里问「还有没有要动的」。

### B. 每一版写好：自查，出提纲卡

1. **自查**（每一版写完都跑）：

```
$PY "agent-tools/view.py" "<项目名>" outline --pane --check
```

   输出里 `check_ok` 为 false：照 `check_problems` 改提纲，改好再跑这一条。`words_sum` 是合计字数（只加最上一级的节）、`total_words` 是目标字数；偏差超出允许范围的，在出卡前那句话里告诉用户，由用户在卡上定调总字数还是调各节的分配。另外 `$PY "toolkit/scripts/commitments_check.py" "projects/<项目名>/outline.md"` 退出码 0。
2. 推进到等确认（第一版出卡前跑一次；之后每改一版，进度还停在等确认，不用再推进）：`$PY "toolkit/scripts/stamp.py" "projects/<项目名>/task_plan.md" --advance gate3_awaiting`（`--advance` 只对任务计划跑，不对提纲跑）
3. 发一句话：提纲第几版写好了（改过的说改了什么），请用户看，要改的直接写在卡上。不贴路径。
4. 按 `yunzhi-card` 出卡：`$PY "agent-tools/card.py" prepare outline "<项目名>"`（右侧挂过就带 `--pane-open`）。prepare 会顺手把这份材料换到右侧给用户看（见 `yunzhi-card` 第 2 步），不用你另外打开。版本、合计字数与目标、没有资料卡片支撑的节、三点都由脚本从提纲里读。出卡之后、用户回答之前别动提纲。
5. 收回答，照 `card.py answer` 的输出：
   - `approved` → 确认记录已写、进度已推进到撰写交付。说 `say` 里那句交接的话（进度笔记里那一行脚本已经记了），加载 `cite-trace`。
   - `not_approved` → 这是共创的一轮：照卡上的意见改（没写意见就问要动哪里，一次问完），做 C，再回到 B 出下一版的卡。只写了意见、意见里没说要动什么（例如「这版可以了」）：照 `next` 不改提纲，说 `say`，等用户回 1（不用重新出卡）。
   - 写作中要大改结构，先回这一步（见文末）。

### C. 按意见改一版

1. 改 `outline.md`：`version` 加一；`revision_log` 加一条 `{v: <新版本>, at: '<现在>', who: agent, what: <改了什么>, why: <为什么>}`；改了的节写 `revision`；三点的改动内容写这一轮改了什么。
2. 回到 B（自查、出卡）。用户想先看进度时，跑 `$PY "agent-tools/progress.py" "<项目名>" --page --pane` 把右侧换回进度页。

用户的意见（第二节太干、三四节合并）= 对当前提纲的迭代，不是确认。

## 对用户说话

> 用户是政策、公共事务、产业经济方向的研究员，不是开发者。本节管你**对用户说出口的每一句话**：普通消息、对话里的提问、进度汇报、阶段交接，卡上留给你填的空，以及给用户看的材料里你自己写的句子。
>
> 本 skill 其余部分用的是内部叫法（文件名、字段名、状态名、脚本名）。干活、写文件、跑命令时照旧用；**说给用户时换成下面词表的右栏**。确认卡、决定卡上的问题、按钮和标签由出卡脚本写，你只填卡上留给你的空，填的空同样按本节写。

**五条原则**

1. 不出现英文内部词、编号和文件名：argument、E4、task_plan.md、hash 这类。需要指代某个东西时，用它的研究员名称加版本，例如「任务计划第 2 版」。
2. 每个内部对象只用一个研究员名称：任务计划、资料汇编、提纲、成稿、资料卡片、参考文献清单。不要一会儿叫正本、一会儿叫 dossier。
3. 流程动作说成「确认 / 修改 / 重新确认」，不说落章、作废、重弹、推进 collecting。
4. 检查结果只说「有什么事需要你知道或决定」，不报检查项名，也不报 PASS/FAIL。
5. 方法论的动作说成它对报告的影响。例如不说「预注册」，说「先把几种可能的结论和判定标准写下来，结论就不会随着证据被挪」。

**引用怎么写**：用户的原话逐字照抄，放进「」或整段放进 `>` 引用块，前面写明这是「你的原话」或「委托原文」；文献和报告的标题放进《》。出卡脚本会扫一遍用词，并把卡上「」里的字和用户写过的话（委托原话、用户发过的消息）逐字核对：对不上的不算引用，照样算你的用词。所以卡上填的空里，「」只放用户原话；你自己的话（包括环节名、章节名）不加引号。

**研究流程的四个环节**：明确任务 · 收集资料 · 拟定提纲 · 撰写交付。确认点：第 1 次确认（任务计划） · 第 2 次确认（资料汇编） · 第 3 次确认（提纲） · 交付确认。

**这一步常说的几句**

- 开场这样说：「第三步：拟定提纲。我先写出第一版请你看；要改的直接写在卡上，我改好再请你看。你确认提纲之后我才开始写。」
- 各节字数加起来和目标对不上时这样说：「各节字数加起来是 X 字，目标是 Y 字，超出了允许的偏差；你想调总字数，还是调各节的分配？」
- 说某一节用了哪些资料时，写资料卡片的标题，或者「这一节用到 3 张资料卡片」，不写卡号。
- 用户提意见（第二节太干、三四节合并）是在改提纲，不是确认；改完这样说：「改好了，这是提纲第 3 版：第三节加了 3.1 增速对比，四、五节换了顺序。合计 8000 字，和目标相符。请你在卡上看一下，还要改就直接写在卡上。」
- 每一版写好、出提纲卡之前：「提纲第 1 版写好了，请你看一下，要改的直接写在卡上；没问题就选确认，我就开始写。」
- 用户在卡上点了确认之后：「提纲第 3 版定下了，我开始写。写的时候要大改结构，会先问你。」

## 出口契约(离开这一步的硬条件)

| # | 条件 | 怎么验 |
|---|---|---|
| E1 | outline.md 符合规格④:frontmatter(kind / version / updated_at / genre / task_plan_ref / total_words / tolerance / revision_log)+ 节点块严格语法;节点 id 唯一永不复用;evidence 只写存在的卡号;空 evidence 的节带 evidence_mode;修订说明一律写 revision 字段 | `outline_check.py` 无 FAIL |
| E2 | 三点写在提纲最后一节 `## 要你认的三件事 {#commitments}`(放在所有节点块之后),60 / 60 / 80 字 | `commitments_check.py "projects/<项目名>/outline.md"` 退出码 0 |
| E3 | 用户确认了提纲:`--advance gate3_awaiting` → `card.py prepare outline` → 用户点「确认」→ `card.py answer` 写确认记录并推进到 `drafting`。你不写确认记录,也不做确认之后的推进 | `pipeline_status.py`:outline 已确认、状态 `drafting` |

## 不变量

- 正本 / 显示分离:只改 outline.md;用户看到的提纲由脚本按它生成。
- 提纲的每个空 evidence 节点都是一次显式决定,不是偷懒出口。
- 卡上留给你的空写实;回答认不出就问清,禁止假定用户选了推荐项。
- ⛔ 不给用户出题。

## 确认之后又要改提纲

确认之后要改提纲(含写作中发现结构问题),或者资料汇编重新确认之后提纲要跟着再确认:照 task-planner「重新确认一份已经确认过的材料」做(提纲推进到 `gate3_awaiting`),出提纲卡照上面 B 的 1–5 小步。只改措辞、没动结构和判断的,用户可以直接确认。
