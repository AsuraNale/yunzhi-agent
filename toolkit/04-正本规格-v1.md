# 04 正本规格 v1(机器面 · 接口冻结)

> **版本:v1.2.1**(2026-10-02)。版本号与文末修订记录的最新一条一致;改本文件就升版并加一条修订记录。
> 本文件是**给脚本和 skill 读的合同**:字段名、类型、枚举、必填规则、示例。
> 变更规则:改本文件 = 改接口,必须同步 `cite_check` / 校验器 / 渲染器 / SKILL.md;改动记进文末修订记录。
> 总原则:**默认值 + 偏离须声明**。凡「可空」的字段,空 = 采用默认;凡「偏离须声明」的字段,偏离时必须有值。
> 命令一律 `python -X utf8 <脚本>`(`python` 由应用指向自带的解释器)。

## 0 通用约定

| 约定 | 规定 |
|---|---|
| 文件格式 | Markdown + YAML frontmatter(`---` 包围);frontmatter 给机器,正文给人 |
| 键名 | 英文 snake_case;渲染时映射中文标签(`render_*` 维护映射表) |
| 版本块(每个正本必有) | `version: <int>` · `updated_at: <ISO8601>` · `revision_log: [{v, at, who, what, why}]` |
| 印章块(需过窗口的正本:task_plan / dossier / outline) | `approval: {status: draft\|awaiting\|approved\|stale, approved_at, approved_by, approval_quote(≤40字), approved_hash, signature?}` · `approved_hash` = 「frontmatter 去**过程字段** + 正文」的 sha256 前 12 位;过程字段 = `approval / pipeline_status / last_turn_at / updated_at / revision_log`(状态机推进、时间戳、**审计留痕**均不作废印章;实质字段与正文任何变化 → 校验器置 `stale`;签名绑定这个值,原来算得出的每一份永远不变 —— `scripts/fixtures/golden_content_hashes.json` 记着 11964e3 时 77 份文档的值,测试逐份核;键是日期、数字键混文字键、yes / no 键混文字键这几种原来算不出来的,v1.1.2 起改用带类型的键算,见 §⑧-7)· `signature`(v1.1.0,可缺)= 应用在用户点「确认」时算好的签名串,由 `stamp.py --approve --signature` 原样写入;**脚本不校验、只原样保留**,校验在应用里。格式与签名载荷见 §⑧-6 与 `docs/signoff-format.md` |
| 唯一 id | 卡 `uid`、登记表 `id`、大纲节点 `id` 永不复用;删除只标 `deprecated: true` |
| 文体 | `genre: survey`(综述型)\| `argument`(论证型);决定若干字段的必填性 |
| 日期 | `as_of` 一律 `YYYY-MM-DD`;时间戳 ISO8601 带时区 |
| 五态 | `fetch_state` / `liveness.state` 取值 `ok \| empty \| gap \| failed \| blocked`(Fetch Honesty) |

项目目录约定:
```
<project>/
  task_plan.md

  references.yaml
  drafts/<deliverable>.md          ← 正文用 [[R###]] 占位
  out/<deliverable>.html|.docx     ← 渲染产物(非正本)= 成稿文件(§⑨-2)

  review/findings-<n>.json · review/report-<n>.md   ← 第 n 轮复核的发现与人读报告
  library/ (sources.yaml · gaps.yaml · rules/ · archive/ · delivery_commitments.md)   ← 库态,跨任务;delivery_commitments.md = 交付的三点(§⑨-3)
```

## ① task_plan.md

**frontmatter**
```yaml
kind: task_plan
version: 1
updated_at: 2026-08-21T14:00:00-04:00
genre: argument                      # survey | argument(文体判定,task-planner 第一式)
stages: [task, sources, outline, delivery]   # v1.1.0 · 可空;空 = 四个环节全有;本版只允许省掉 outline
scope_brief: H 省县级，含乡镇，不含村 · 2021–2025 年   # v1.2.1 · 研究范围的一句话摘要,≤30 字,上进度面板(§⑨-4)
report_name: 内参                   # v1.2.1 · 可缺;成稿叫法,用户的说法,≤6 字,上首页项目卡;问过报告类型卡时与卡上的 report_name 一字不差(§⑨-4)
pipeline_status: gate1_awaiting      # 见状态机
approval: {status: awaiting, approved_at: null, approved_by: null, approval_quote: null, approved_hash: null}
budget: {cards_max: null, steps_max: null, words_max: 10000}   # 可空;超限只提示不拦
evidence_standard:                   # 不偏离 → inherit: true 且其余为空
  inherit: true
  primary_tiers: null                # 偏离时必填,如 [A, A-, B]
  scope_note: null                   # 偏离时必填:适用于哪类主张
classification_frame: null           # 用户给的分类框架(如「三类渠道形态」),可空
constraints: {words_max: 10000, formats: [html, docx], deadline: null}   # words_max 只写正整数;它与 formats 拼成面板的「成稿形式」(§⑨-4);formats 是用户要拿到的格式 —— 网页版与 Word 版两种成稿总是都生成(应用预览要网页版,交付卡两种都列)
last_turn_at: 2026-08-21T14:00:00-04:00
revision_log: []
```

**pipeline_status 状态机**(只能前进;重过窗口时回到对应 `*_awaiting`):
`planning → gate1_awaiting → gate1_approved → collecting → gate2_awaiting → gate2_approved → outlining → gate3_awaiting → gate3_approved → drafting → verifying → delivered`

**`stages`(流程环节,v1.1.0)**:本项目有哪几个环节。机器键 → 用户叫法 → 过哪个窗口 → 占哪几个状态:

| 键 | 用户叫法 | 窗口 / 正本 | pipeline_status 取值 |
|---|---|---|---|
| `task` | 明确任务 | 对接窗口1 · task_plan.md | planning · gate1_awaiting · gate1_approved |
| `sources` | 收集资料 | 对接窗口2 · dossier.md | collecting · gate2_awaiting · gate2_approved |
| `outline` | 拟定提纲 | 对接窗口3 · outline.md | outlining · gate3_awaiting · gate3_approved |
| `delivery` | 撰写交付 | 交付确认(不落印章;交付记录与推进到 `delivered` 都由应用在用户点「交付」时做,§⑦) | drafting · verifying · delivered |

- 缺这个键或值为 `null` = 四个环节全有(v1.0.6 及以前的项目都是这样,行为不变)。
- 值必须是按上表顺序排列、不重复的列表。**本版只允许省掉 `outline`**,即只有 `[task, sources, outline, delivery]` 与 `[task, sources, delivery]` 两种合法值;其他一切(不是列表、未知键、重复、乱序、省掉别的环节、空列表)都是「读不出」—— 各工具报错并**按四个环节全查**(最严),不当作「省掉了」。
- 省掉 `outline` 的项目:`outlining` / `gate3_*` 不是合法状态;`gate2_approved` 之后直接 `drafting`;不需要 outline.md 的确认记录。
- `stages` 是实质字段,进印章 hash:改流程 = 改了已确认的任务计划,必须重新过对接窗口1。
- **只改流程(v1.2.0)**:已确认的任务计划只改 `stages` 时,走改流程卡(§⑦ `flow_change`),不走完整的任务计划确认。这一版只许动:`stages`、`version`(加一)、`revision_log`(加一条,`what` 写改动环节那一句)以及过程字段 `approval` / `pipeline_status` / `updated_at` / `last_turn_at`;其余 frontmatter 键与整个正文(含 `{#commitments}`,§⑨-1)一字不动 —— 应用拿它与上次确认时存档的那一版比,多动一处就退回,要走完整的任务计划确认。不先 `--invalidate`、状态不推进:用户点「先不确认」时把 `stages` 与 `version` 改回原值,内容 hash 回到原来的值,原来的确认记录就照旧有效;这时追加的那条 revision_log 的 `v` 写那个没被确认的版本号,**不许更大**(更大的话 revision_log 里的最大 `v` 超过下一次要确认的版本,§⑧-1 的落章守卫会拒绝应用落章),以后再改照常从当前版本加一。改流程那条 revision_log 的 `what` 以「改流程：」开头:agent 重启时开场检查因任务计划确认后又改过而退出码 1 是预期的 —— 最后一条是「改流程：」、`v` 等于当前 `version`,就是改流程卡还在等用户,用同一个 `id` 再弹。只在任务计划确认过、还没进拟定提纲时用(`pipeline_status` 为 `collecting` / `gate2_awaiting`);任务计划还没确认过时直接改,随任务计划卡一起确认。
- 各工具的具体行为见 §⑧-5;完整说明见 `docs/stages.md`。

**正文固定节**(H2 标题 + `{#id}`,校验器按 id 查)

| 节 | id | 必填 | 内容 |
|---|---|---|---|
| 原始请求 | `request` | 必 | 用户原话(引用块) |
| 文体判定 | `genre_rationale` | 必 | 为何 survey/argument;v1.2.0 起记报告类型卡(§⑦ `report_type`)上用户的选择:下判断 → `argument`,梳理情况 → `survey`,先不定 → 先按 `argument` 写并写明「你说先不定」 |
| 可证伪命题 | `thesis` | 必 | 改写后的命题(不得把原句当真) |
| 假设 | `hypotheses` | argument 必 | ≥2 条(如强/弱) |
| 预注册结论空间 | `preregistration` | argument 必;survey 由提议决定 | 表:`outcome(A/B/C) · 判定条件 · 对应表述`;v1.2.1 起「对应表述」只能写 成立 / 部分成立 / 不成立 —— 资料汇编卡上的初步结论就按它显示(§③「上卡的字段」;`commitments_check.py` 对任务计划核这一栏) |
| 证据对接窗口条件 | `evidence_gate` | argument 必 | 不成立时的动作(如「第二阶段取消」) |
| 概念定义表 | `definitions` | 必 | 表:`概念 · 操作定义 · 不算作证据的情形` |
| 项目口径 | `scope` | 必 | 产业口径 / 时间窗 / 地域层级;frontmatter 另有它的一句话摘要 `scope_brief`(v1.2.1,§⑨-4) |
| 证据标准 | `evidence_standard` | 必 | 不偏离:一行「沿用默认规范：一手资料优先，来源分官方一手、机构自报、二手三类」(这一节用户在阅读页上看得到,所以用研究员的话;v1.2.0 前写的「继承纪律库:一手优先,A/A−/B」照样算不偏离);偏离:写明放宽内容与适用主张类型 |
| 分类框架 | `classification` | 可 | 用户自制分类 |
| 约束 | `constraints` | 必 | 字数/格式/时限 |
| 预算与止损 | `budget` | 可 | 上限与"超限动作 = 停下问用户" |
| 要你认的三件事 | `commitments` | 必 | 正文最后一节,三点,写法与上限见 §⑨-1 |

## ② cards/<uid>.md(一卡一文件)

**frontmatter**
```yaml
kind: card
uid: S10                              # 稳定;项目内唯一;永不复用
title: 华瀛控股·跨媒介 IP 生态
stance: support                       # support | counter | mixed | gap(封闭四值)
tags: [linjiang, huaying, ip, content]   # 自由主题标签
as_of: 2026-08-04
version: 1
facts:                                # 数值 + 口径成对;gap/机制型卡可为空列表
  - {value: "持有星澜文学 56.55%", caliber: "华瀛控股 2025 年报,截至 2025 年末", cited: true}
  - {value: "星澜文学 IP 商品 GMV 超 11 亿元", caliber: "星澜文学全国业务;星澜注册与主要运营不在临江市", cited: true}
sources:
  - url: https://example.com/filings/2026/xinglan-ar2025.pdf
    title: 星澜文学 2025 年报
    tier: A                           # A | A- | B(封闭三级;挂在来源上,卡不带 level)
    locator: "p.37 合并利润表"          # facts 中任一 cited:true 的来源必填;背景来源可空;粒度可粗
    as_of: 2026-08-04
    fetch_state: ok                   # 五态
    inherited_from: null              # 可选;本轮**沿用既有取证**时必填(如 "上一轮尽调 C001")。
                                      # 五态里没有「继承」这一态,不填就与「本轮实取」同形
    note: null                        # 细微差别(原 A/B+ 之类)放这里
revision_log: []
```

**正文固定节**:`## 可支持观点 {#support}`(渲染标题可随卡性质显示"互动机制"等)· `## 局限 {#limit}`(**必填非空**;允许「无重大局限（理由）」)

**`stance` 在界面上的叫法(v1.2.1)**:`support` → 支持判断 · `counter` → 不支持 · `mixed` → 背景资料 · `gap` → 资料缺口(与 `wording/glossary.json` 里 gap 的叫法一致)。资料汇编卡上的卡片构成、资料卡片页都按这四类数;参考实现 `pipeline_lib.STANCE_LABELS`。

**校验规则(card_check)**:uid 唯一 · stance ∈ 四值 · limit 非空 · sources[].tier ∈ 三级 · 凡 `facts[].cited: true` 至少一条来源带 locator(无 → FAIL;cited 数 > 2× 带 locator 来源数 → WARN;**caliber 以卡号/前两轮档案为出处 → WARN「D8 卡号终点引用」**) · `stance: gap` 允许 facts/sources 为空 · 非 gap 卡至少一条来源 · fetch_state ∈ 五态 · **措辞提示沿用既有取证(继承/沿用/与上一轮一致…)但无 `inherited_from` → WARN「继承未标注」** —— 典型形态:卡写着 `fetch_state: ok` + 本轮 `as_of`,而本轮从未打开过那份源文件

## ③ dossier.md(汇编综合)

**frontmatter**
```yaml
kind: dossier
version: 4
updated_at: ...
genre: argument
approval: {status: awaiting, ...}
dashboard:                            # 预算仪表盘,汇编综合步骤写入(键名见下表,cite_check ⑧ 按键名判)
  cards_count: 74
  steps_used: 212                     # 从 out/session_facts.json 逐值抄,⛔ 不许自报、取不到写 null 不写 0
  session: "yz-main-01"               # ↓ 三个出处字段:与同一份 session_facts.json 逐值同源
  session_picked_by: "DSH_SESSION_ID(harness 注入)"
  captured_at: "2026-09-04T12:00:00.000Z"   # 加引号;不加引号 YAML 会读成日期时间(cite_check 会归一,但照抄最稳)
  budget_ref: task_plan.budget
claims:                               # 结论层的机器面(正文另有人读版)
  - {id: C3, strength: medium_strong, evidence: [S4, S10, S11], rule_trace: "独立来源3·本地闭环1·指标不完整→中强", override_reason: null}
rules_candidates: [R1, R2, ...]       # 边界层红线候选 id(正文有文本)
gate_verdict: {outcome: B, reason: "...", counterexample_criteria: "..."}   # argument 必;survey 为 null
gaps: [{id: G1, what: "临江市服装业专项出口数据", state: gap, owner: null}]
revision_log: []
```

**`dashboard` 的机器面键名**(v1.1.0 补全;cite_check ⑧ 逐键判,写成别的名字 = 没写):

| 键 | 类型 | 来源 | ⑧ 怎么判 |
|---|---|---|---|
| `cards_count` | 整数 | 汇编时的卡数 | 由 ⑩ 对 cards/ 实数核;超 `budget.cards_max` → WARN |
| `steps_used` | 整数或 null | `session_facts.json` 的 `steps_used` | null/缺 → WARN「未取到」(⛔ 不当 0);有数而无 json → WARN「等于自报」;json 读不出 / json 里不是整数 → WARN;与 json 不符 → **FAIL**;`'7'` 与 `7` 视为相等;只认 ASCII 数字(`'²'` `'①'` `'７'` 与 `.nan` / `.inf` 都不是整数,按「未取到」报,v1.1.1) |
| `session` | 字符串 | json 的 `session` | 三个出处字段缺任一 → WARN;任一与 json 不符 → **FAIL** |
| `session_picked_by` | 字符串 | json 的 `session_picked_by` | 同上 |
| `captured_at` | 字符串(带时区 ISO-8601) | json 的 `captured_at` | 同上;YAML 读成日期时间的,先归一成 json 的写法(UTC、毫秒三位、尾随 `Z`)再逐字比 |
| `budget_ref` | 字符串 | 固定 `task_plan.budget` | 不判 |

**上卡的字段(v1.2.0)**:研判型(argument)资料汇编的 `gate_verdict` 上资料汇编卡「对照判定标准,初步结论」那一行 —— `outcome` 由应用按任务计划判定标准表第三栏「对应表述」写(只能是 成立 / 部分成立 / 不成立,§①;表读不出时缺省 A / B / C = 成立 / 部分成立 / 不成立),`reason` 是理由,**≤60 字**(码位数,数法同 §⑨-1),用研究员的话写,不放卡号、不放 `[[R…]]`。超了应用退回(§⑦)。综述型没有这一行。

`dashboard` 必须是映射;写成字符串/列表 → ⑧ 报 WARN「不是映射」,步数按「未取到」处理(不崩)。`task_plan.budget` 同理;`steps_max` / `cards_max` 写成带引号的数字按数字比(只认 ASCII 数字),读不出的上限报 WARN「预算读不出」,⛔ 不落进「预算内」。

**正文六层(H2 + id,顺序固定)**

| 层 | id | 必填 | 内容 |
|---|---|---|---|
| 定义与口径头 | `header` | 必 | 从 task_plan 复现:操作定义表 · 证据等级 · 预设闸门(argument) |
| 结论层 | `claims` | 必 | 每条候选命题:`C# · 文本 · strength(strong/medium_strong/medium/weak)· evidence[uid] · 按规则推导一行`;规则外判断须写 `override_reason` |
| 边界层 | `boundaries` | 必 | 口径红线候选(R#,带文本与来源 uid)· 不能过度推断(list) |
| 内容层 | `content` | 可 | 按课题定形:比较表 / 二维表总集 / 其他(节名可配置) |
| 闸门层 | `gate` | argument 必 | 预设闸门复述 · 判定 A/B/C 与理由 · **反例纳入标准** |
| 下一步层 | `next` | 必 | gaps/补证清单(带五态);survey 另有政策选项 |
| 索引层 | `index` | 必 | 去重来源表,可跳转 |

六层之后、正文最后一节是 `{#commitments}`(三点,§⑨-1);第 3 点写写作时最容易越过资料能支持的范围的地方。

**聚合规则默认(可配置,写在 `library/rules/aggregation.md`)**:strong = ≥3 独立来源 + ≥1 可核验本地闭环样本 + 可观察经营指标;medium_strong = 前两项满足、指标不完整;medium / weak 依次递减并注明缺项。

**质量底线**(结构与密度):六层齐 · 结论层 ≥5 条 · 边界层 ≥5 条 · 索引 = 去重来源 · 每卡带链接 · 每节有锚点。

## ④ outline.md(大纲正本)

**frontmatter**
```yaml
kind: outline
version: 3
updated_at: ...
genre: argument
task_plan_ref: task_plan.md#v1        # 方法论对接窗口引用,不重复写
total_words: 16000
tolerance: 0.10                       # 节点和偏差 >10% 只提示不拦
approval: {status: awaiting, ...}
revision_log: []
```

**正文节点块语法**(严格,`render_outline.py` 解析):

**校验规则(outline_check)**:节点 id 唯一 · evidence 中每个 uid 存在于 cards/ · survey 节点 evidence 必非空(**综合/收束节点例外:空 evidence 须带 `evidence_mode: synthesis`**)· argument 节点空 evidence 须带 evidence_mode · Σwords 与 total_words 偏差 > tolerance → 提示(非 FAIL)

**提纲卡与面板上的两个数(v1.2.1;outline_check、cite_check ⑨ 与应用同一个算法)**:

## ⑦ 确认点与卡片的机器面(v1.2.0 改写)

- 确认点与正本:第 1 次确认 → task_plan · 第 2 次 → dossier · 第 3 次 → outline(`stages` 省掉提纲时没有)· 交付确认 → 成稿(不落 `approval`;交付记录由应用写,格式见 `docs/signoff-format.md`)。确认记录写入各自 frontmatter 的 `approval`。
- **确认只由人做**:用户在卡上点「确认」或「交付」时,由应用写带签名的确认记录或交付记录(§⑧-6)、推进状态、存档那一版。agent 不写确认记录,也不做确认之后的那一步推进(task_plan → `collecting`;dossier → `outlining`,省掉提纲时 `drafting`;outline → `drafting`;交付 → `delivered`)。agent 自己写的确认记录没有有效签名,应用会标为「需要重新确认」。
- **agent 在确认点做的**:写好正本与它的三点(§⑨-1;交付的三点是 `library/delivery_commitments.md`,§⑨-3)→ `stamp.py <project>/task_plan.md --advance gateN_awaiting`(交付:成稿写完、开始检查时 `--advance verifying`)→ 调 `ann_gate_card` 请应用弹卡。
- **卡片**:`ann_gate_card` 的参数 = `id` + `kind` + 该 kind 的字段(类型细节以 `docs/engine-protocol.md` 为准)。`id` 由 agent 起,同一张卡被退回后再弹用同一个 `id`。字数按 §⑨-1 的数法。

| kind | 什么时候 | agent 给的字段(上限) | 用户点了之后 |
|---|---|---|---|
| `report_type` | 明确任务,写任务计划之前 | `report_name` ≤6(成稿叫法,用用户的说法)· `thesis` ≤40(核心判断,一句能用资料检验的话)· `why` ≤80(必须含「」引的用户原话,逐字)· `recommend`:`judge` 或 `survey`,不推荐就不给这个键 | 选择交回 agent:下判断 → `genre: argument`;梳理情况 → `survey`;先不定 → 先按 `argument` 写 |
| `task_plan` | 任务计划写好或改好 | 无 | 确认 → 应用落确认记录、推进到 `collecting`;先不确认 → 回 agent |
| `dossier` | 资料汇编写好 | 无 | 确认 → 推进到 `outlining`(省掉提纲时 `drafting`);先不确认 → 回 agent |
| `outline` | 提纲改到用户满意 | 无 | 确认 → 推进到 `drafting`;先不确认 → 回 agent |
| `delivery` | 成稿写完,交付前检查全过,复核结果对得上当前成稿且必须改为 0(§⑨-2) | 无 | 交付 → 应用写交付记录、推进到 `delivered`;先不交付 → 回 agent |
| `decision` | 做到一半要用户拿主意 | `question` ≤40(必须是一个选择)· `why` ≤80(卡在哪里、不问会怎样)· `options` 2–3 个,每个 {`label` ≤20, `effect` ≤40, `changes_plan` 真或假} · `recommend`:从 1 数的选项序号,不推荐就不给这个键 | 回 agent;选了 `changes_plan` 为真的 → agent 改任务计划,再走任务计划卡(只改了流程时走改流程卡) |
| `flow_change` | 用户说不要某一步(本版:不拟提纲,或把它加回来) | `changes` ≤60(改动环节:去掉或加回了哪一步) | 确认 → 应用落确认记录并存档,状态不动;先不确认 → agent 把 `stages`、`version` 改回原值(§①) |

- 确认类(`task_plan` / `dossier` / `outline` / `delivery`)不收 `question` / `detail` / `options` / `approve` / `header`:卡上的问题、版本、张数、字数、初步结论、三点都由应用从正本与机器输出读。
- 弹卡之前应用先验:字数上限、用词(`wording` 扫描器)、引用用户原话必须逐字、该读的正本在且读得出、三点齐全(§⑨-1)、交付门槛(§⑨-2)、改流程只改了流程(§①)。不过就不弹、退回 agent:agent 收到一个工具错误,内容就是应用的那句话 —— 照它改,用同一个 `id` 再弹。
- 用户看卡期间正本又被改了 → 应用不签,按新内容重新准备卡。所以弹卡之后、用户回答之前别动那份正本。
- **回答的形状**(v1.2.1,应用交回 agent):确认类与 `flow_change` → `{id, kind, approved: true|false, custom?}`;`report_type` → `{id, kind, selected: 'judge'|'survey'|'undecided'|null, custom?}`;`decision` → `{id, kind, selected: <从 1 数的选项序号>|null, custom?}`。`custom` 是用户附的话;`selected: null` = 用户没点选项、只写了意见。`undecided` → agent 先按 argument 写,并说明确认任务计划时还能改。被退回的卡不是回答,是一个工具错误,内容就是应用的那句话。
- **`id`**:同一次弹卡请求,被退回后再弹用同一个 `id`(哪怕为了过检查改了材料);卡真的弹出来、用户点了「先不确认」,改好之后是新的一版、新的 `id`(`task-plan-v2` 之后是 `task-plan-v3`)。交付卡 `delivery-<n>` 的 n 数的是真正弹出来过的交付卡,被退回的不算。
- 没点「确认」= 没确认;用户的任何话都是意见,不是确认。察觉「往下走」的语气就主动弹卡;拿不准就问。
- `pipeline_status.py`(开场仪式):新会话首轮或 `last_turn_at` 距今 > 6h → 读三正本 approval/hash + task_plan.pipeline_status + PROGRESS.md → 输出一行状态 + 不一致项;不一致就停下来向用户说明。

## ⑧ 工具行为契约(脚本已实现,写明以便对账)

本节记录几条**已在 `scripts/` 里强制、但正文其余各节没有写明**的机器行为。改脚本前先看这里。

### ⑧-1 落章守卫(`stamp.py --approve`)

**三类**情况**拒绝落章**,退出码 2,且**拒绝时不写盘**(文件字节不变):

1. `revision_log` 里声明的最大 `v` **大于** frontmatter 的 `version` —— 意思是这一轮改动没有升版,卡上的版本号会停在旧版本而正本已经走到新版。改法:先升 `version`,再请用户确认(v1.2.0 起落章由应用在用户点「确认」时做)。
2. `version` 或任一条 `revision_log[].v` **不是整数**(字符串、布尔、缺字段都算)。版本读不出来就判断不了有没有升版,一律拒绝,不当作「没声明」跳过。
3. `revision_log` **不是列表**(写成映射、散文字符串、整数),或其中任一条**不是键值映射**(散文条目、嵌套列表)。形状不对 = 版本声明读不出来,同样拒绝 —— 原来这里是个过滤器,少一个 `-` 就整条跳过守卫落章。

同批的配套行为:`--invalidate` 遇到非整数 `version` 同样 rc 2 拒绝(不抛异常);`pipeline_status` 遇到非整数 `version`(含布尔)报 WARN「version 不是整数」,不抛 traceback。

v1.1.0 起 `--approve` 另有三个参数给应用用(`--at` / `--expect-hash` / `--signature`,见 §⑧-6),以及一条流程守卫:task_plan 的 `stages` 省掉了提纲时,对 outline.md 的 `--approve` 拒绝(rc 2,不写盘)。

v1.1.1 起再加一条:正本上已有**带签名**的确认记录时,不带 `--signature` 的 `--approve` 拒绝(rc 2,不写盘)—— 否则签名被静默覆盖、不留痕迹。确有需要显式加 `--replace-signed --why "<为什么>"`(`--why` 必填)。替换带签名记录时旧记录怎么留,见 §⑧-6。

⚠ 这道守卫**只覆盖对接窗口1–3 的 `--approve`**。交付走的是 `--advance delivered`,没有这道守卫;`--advance` 不读 `version`。v1.2.0 起 `--approve` 与确认之后的推进(含 `--advance delivered`)都由应用跑,交付的把关在应用(交付记录,`docs/signoff-format.md`;门槛见 §⑦)。

### ⑧-2 运行事实由机器取(`session_facts.mjs`)

`dossier` 的 `dashboard.steps_used` **由机器从会话日志取,不许 agent 自报**:

- 口径 = **主会话在取数那一刻**的步数(`step/start` 事件数);含子代理的合计另记一个字段,**不进预算判断**。
- 同时记下会话 id、选法(环境变量注入 / 启发式)与取数时刻,否则读报告的人无法复核选中的是哪个会话。三个值逐值抄进 `dossier.dashboard`(键名见 §③ 表)。
- 取不到时写「未取到」,**不许写 0**。0 会被读成「真的是零步」。

**会话日志在哪、怎么选**(v1.1.0 按 dsh 0.1.7-rc.2 适配):

- 会话根 = `$DSH_HOME/sessions`;`DSH_HOME` 未设或为空白时是 `~/.dsh/sessions`(与 dsh 自己的规则相同)。
- 其下两层目录 `<项目目录键>/<会话目录>/`,会话目录名 = 会话 id 逐字符转义(不安全字符写成 `~XXXX`);日志文件 `session.v<N>.jsonl.zstd`(不压缩时无 `.zstd`;旧版 `session.jsonl.zstd`)。一个会话目录里有几代日志时**只读代数最高的一份**。
- 日志是若干独立 zstd 帧首尾相接(按帧头结构切帧,不按魔数切);首行 header `{type:"session", version, id, createdAt, cwd?, parentSession?, origin?, isSeeded, delegationDepth}`,其后每行一个事件 `{type, seq, time, data}`。读 `step/start` 与 `tool/call`(`data.name`、`data.arguments`)。
- 选法按优先级:`DSH_SESSION_JSONL`(旧版注入)> `DSH_SESSION_ID`(harness 注入)> `--session <片段>` > 启发式(最新一份提到本项目的**顶层**会话)。⛔ 注入的变量**设了却无效**(文件不在、会话根下找不到这个 id)时**不回落**,退出码 3,json 的 `session_pick_error` 写明原因。
- 子代理按 header 的 `parentSession` 递归归并(子代理的目录名与逻辑 id 两种写法都认);子代理开头从父会话继承来的事件(`session/end-seed` 且 `data.inherited: true` 之前)不重复计入。
- shell 工具 `pwsh` 与 `bash` 一样计数,统称「shell 调用」。

**退出码**:0 取到 · 2 用法错 · 3 未取到会话日志(含注入变量无效)· 4 结果已算出并打印,但 `--json` 没写成(那份 json 不能用;同一路径上的旧 json 能删就删,删不掉会明说)。非 0 一律表示「不能拿这份 json 核 dossier」。

**`session_facts.json` 键名**(cite_check ⑧ 读前四个;项目外文件的清单与计数怎么列见 ⑧-3):

| 键 | 类型 | 说明 |
|---|---|---|
| `session` | 字符串 / null | 选中会话的目录名 |
| `session_picked_by` | 字符串 / null | 选法(带「harness 注入」「--session」「启发式」字样) |
| `captured_at` | 字符串 | 取数时刻,UTC ISO-8601,毫秒三位、尾随 `Z` |
| `steps_used` | 整数 / null | 主会话 `step/start` 数;未取到为 null |
| `steps_incl_subagents` | 整数 | 主会话 + 全部后代子代理 |
| `subagent_sessions` | 字符串列表 | 并入的子代理会话目录名 |
| `sessions_root` | 字符串 | 实际读的会话根 |
| `toolkit_root` | 字符串 / null | 工具包根(比较用的形态:正斜杠,Windows 下全小写);取不到为 null |
| `outside_reads` | 列表 / null | 项目目录外的路径,每条 `{path, tool, action(读/写), scope, hint, from(主会话/子代理), session, turn}`;未取到为 null |

### ⑧-3 项目外读取清单按 scope 分组

项目外读取清单(v1.2.0 起由应用列在确认卡的「这一轮我读过的项目以外的文件」里,不再有窗口报告)按四类分组:工具包之外(`outside_toolkit`)/ 运行时临时目录(`harness_temp`,只认 `dsh-spill-*` 目录)/ 同工具包内的别的项目(`other_project`)/ 工具包内部文件(`toolkit_internal`)。取不到工具包根时是第五个值 `unclassified`:不分组,逐条全列并写明原因。

- **逐条列**:第一类的全部条目;以及**任何分组里的项目外写入**(`action` 为「写」)—— 不论 scope,写入一条都不折叠(立规的案例 `write scripts/liveness_probe.py` 就是 `toolkit_internal` 的写入)。
- **折叠成计数**:其余三组的**纯读取**。
- **JSON 输出保留全部条目**,不折叠。

⛔ 这份清单是**下限不是全集**:shell 工具(`pwsh` / `bash`)的命令行未解析,相对路径的读取也不在内。措辞必须写「至少读了这些」。取不到会话日志时写「未取到会话日志」,**不要留空清单**——空清单会被读成「没有越界」,那比不写更糟。

### ⑧-4 出口契约表的结构判据

每份 skill 的「出口契约」表由 `test_skill_contract.py` 按结构校验,不是按文字:

- 每条出口行必须是**完整三格**且**写在一行内**(跨行会让 markdown 表格在那里断掉,第三格任何解析器都读不到);
- 「怎么验」格不许为空;
- 出口行之间不许夹散文,最后一条出口行之后也不许;
- 表下的附注必须挂在自己的 `## ` 标题下(三级标题 `### ` **不终止**上一节,附注会被并进最后一条出口条件);
- 闭合竖线之后不得再有文本(界面按竖线切格,多出来的那格会被静默丢弃)。
- 「可解析」按**面板那把尺**量:面板从第一个以 `## 出口契约` 开头的行起算,所以那一行必须就是严格形的主标题 `## 出口契约(…`(`test_contract_panel_parse.py` 移植面板解析器逐条核)。

### ⑧-5 流程环节 `stages` 在各工具里的行为(v1.1.0)

| 工具 | 缺省四环节(含老项目) | 省掉提纲 `[task, sources, delivery]` | `stages` 读不出 |

### ⑧-6 确认记录的签名字段(v1.1.0 · 设计决定 D1「确认只能由人做」)

- 字段:`approval.signature`,一个字符串,只许 `A–Z a–z 0–9 . _ ~ : + / = -`,1–4096 个字符;没有签名时**不出现这个键**。
- 写入:只经 `stamp.py <正本> --approve --by <人> --quote <原话> --at <带时区 ISO-8601> --expect-hash <12 位 hash> --signature <签名串>`。给了 `--signature` 就必须同时给 `--at` 与 `--expect-hash`,且 `--quote` 不得超过 40 字;`--expect-hash` 与当前内容 hash 不符 → rc 2 不写盘(应用算签名之后正本又变了)。`approved_at` 写 `--at` 的原串,`approved_hash` 写当前 hash(= `--expect-hash`)。
- 保留:脚本**不校验签名**,只原样保留。`--advance` 不碰 `approval`;`--invalidate` 把作废前的整条确认记录(含 `signature`,逐字)挪进新 revision_log 条目的 `prev_approval`,`approval` 回到 awaiting、不带签名。`signature` 在 `approval` 里,`approval` 是过程字段,所以签名不进内容 hash,`--check` 不受影响。
- 不许无痕覆盖(v1.1.1):正本上已有带签名的记录(`signature` 在且不为 null,不看 `status`)时,不带 `--signature` 的 `--approve` rc 2 不写盘,除非显式 `--replace-signed --why`。凡是 `--approve` 替换了带签名的记录(新记录带不带签名都算,应用重新确认也算),旧记录整条、逐字挪进新追加的 revision_log 条目:`{v: 当前 version, at, who: app|agent(按新记录有没有签名填), what, why: --why 或 null, prev_hash, prev_approval}`。`v` 记当前版本(正文没动,不升版,不会绊倒下一次落章的版本守卫)。
- 签名载荷(应用签名与校验时用;脚本侧有参考实现 `pipeline_lib.signoff_payload`):UTF-8 编码的 JSON 数组、无空白 ——
  `["yunzhi-signoff/1", <项目 id>, <正本文件名>, approved_hash, approved_at, approved_by, approval_quote]`,与 Node 的 `JSON.stringify(数组)` 逐字节相同。签名串的建议写法、密钥与校验流程见 `docs/signoff-format.md`。

### ⑧-7 读不出的值:照实报,不崩(v1.1.1 起)

脚本崩了 = 没有报告、没有 `--json`,读的人看到的是「什么都没说」而不是「拦住了」。下面几种手写出来的形态照实报告:

- `approval` 不是键值映射(`approval: approved` 这类标量、列表):`pipeline_status` 报 `[FAIL] 印章: <正本>: approval 不是键值映射…`,facts 里该正本记 `draft`(读不出的确认记录不算确认);`cite_check` ⑥ 报 `[FAIL] 三印章`;`stamp.py --check` 退出码 1,第一行照旧是 `…: 印章无效(status=None)`,说明另起一行。
- 不加引号的时间(YAML 读成日期 / 日期时间,如 `approved_at: 2026-09-29T14:03:11-04:00`):报告与 `--json` 里按 ISO-8601 字符串归一(Python `isoformat()`;最常见的带时区 `T` 形归一后与加引号时逐字相同)。只在读出来用的地方归一,写回正本不改写法;内容 hash 的算法不变。
- `task_plan.last_turn_at` 不带时区(含不加引号的日期):`pipeline_status` 报 WARN「时间」,不算距上轮时长。
- cite_check ⑧ 的数字只认 ASCII 数字(见 §③ `dashboard` 表)。
- `revision_log` 形状不对(不是列表;或某一条不是键值映射):`pipeline_status` 报 `[WARN] 留痕: <正本>: revision_log 现在是<类型>,不是列表(第 N 行)` / `revision_log 第 K 条现在是<类型>,不是键值映射(第 N 行)`(类型说成「一个映射」「一段文字」「一个数字」「一个列表」……),不挡推进;落章时 `stamp.py` 照 §⑧-1 第 3 类拒绝(v1.1.2)。
- `updated_at` 或 `revision_log[].at` 是读不出的时间(加了引号的不存在日期如 `'2026-02-30'`,或不是 ISO 8601 的写法):`pipeline_status` 报 `[WARN] 留痕: <正本>: 第 N 行的 <字段> 读不出时间(…)`。原来静默跳过,「晚于写入时刻」那条检查也就看不见它(v1.1.2)。
- frontmatter 整个读不出来 —— YAML 写法有误;按类型构造不出来的值(不加引号的不存在日期或时刻 `2026-02-30`、`2026-13-01`、`25:00:00`,标了 `!!int` 却不是整数……,PyYAML 构造时就失败);frontmatter 不是键值映射;文件不是 UTF-8 编码:`pipeline_status` 报一条说明,`--json` 照常写出(v1.1.2)。
  - 能定位时说明里带文件行号:写法有误、读不出的值、不是 UTF-8 → 出问题的那一行;不是键值映射 → frontmatter 所在的那几行。行号按文件里的换行算(PyYAML 自己的行号把值里的 U+2028 / U+2029 / NEL 也当换行,所以按它给的字符位置换算)。定位不到时(少见:构造失败却找不出是哪个值)只说「有一个值读不出来」,不带行号。
  - `task_plan.md` 读不出:`[FAIL] 状态机: task_plan.md: frontmatter 读不出来 —— …`;facts 与 `task_plan.md` 不存在时同形(`pipeline_status`、`stages` 为 null,`stamps` 为空),但 `stages_error` 写原因 —— 流程环节是「读不出」,不是「缺省」。
  - `dossier.md` / `outline.md` 读不出:`[FAIL] 印章: <正本>: frontmatter 读不出来 —— …`,该正本记 `draft`(读不出的确认记录不算确认);**这份正本**的其余检查(版本、留痕、时间)跳过,其他正本与全项目的检查照常。
  - 计数读的卡片或 `references.yaml` 读不出来(YAML 写坏、日期不存在、不是 UTF-8、卡片的 frontmatter 是列表、`entries` 不是键值映射的列表):该计数为 null(「没能数」,面板显示未产出),并报 `[WARN] 留痕: cards/<卡>: …` 或 `[WARN] 留痕: references.yaml: …`;卡片的其余毛病由 `card_check` 报,登记表的由 `cite_check` 报。
  - `PROGRESS.md` 不是 UTF-8:`[WARN] PROGRESS: PROGRESS.md 不是 UTF-8 编码,读不出来`,facts 的 `progress_first_line` 为 null。
  - 读法不变:不把不存在的日期改读成文字 —— 应用的 YAML 读法与 `read_md` 逐值对拍,改了两边就会对同一份文件给出两个答案。只动了 `revision_log`、`updated_at` 这类过程字段的,改好后原来的确认照样有效(它们不进内容 hash)。
  - ⚠ 本版只修了开场仪式 `pipeline_status`(以及各脚本共用的内容 hash,见下一条)。`stamp.py`(`--check`、`--approve`)与 `cite_check` 遇到读不出的 frontmatter 仍然抛异常退出(不写盘)。仍会让 `pipeline_status` 抛异常、没有 `--json` 的(没修,记在这里):`out/` 里损坏的 docx;嵌套几千层的 YAML(超出递归深度);自己引用自己的锚点(`a: &x [*x]`,内容 hash 序列化时报循环引用)。
- **说明只说是什么、在第几行,不引正本里写的东西**(v1.1.2 复核):上面 v1.1.2 这几条(`revision_log` 形状、读不出的时间、frontmatter 读不出来、卡片与登记表读不出来),连同「时间戳」那条 WARN(声称的修改时刻晚于文件写入时刻:`第 N 行的 <字段> 比文件写入时刻晚 … 分钟`),只说字段、类型、行号和哪一类毛病 —— 不引写的值,也不引 PyYAML 或 Python 异常自己的说明:它们会带原文(`invalid literal for int() … '<原文>'`、锚点名)和文件的完整路径。报告会进 `--json`、进应用;`revision_log` 里装的常常就是确认记录(谁、原话),截断的片段应用遮不住。文件名照写(`cards/<卡>.md` 这类,用来指位置)。
- 键是日期的映射(`milestones: {2026-10-01: 初稿, 2026-10-14: 交付}`)、数字键混着文字键、YAML 1.1 的 yes / no 键混着文字键:json 写不出这种键或排不了序,内容 hash 原来抛 TypeError —— `pipeline_status` 与 `stamp.py --hash / --approve` 都崩,这样的正本永远确认不了。v1.1.2 起只有这几种原来算不出来的改用带类型的键(每个映射写成按「键的文字、键的类型」排好序的列表,前面加一个标记,与原来以 `{` 开头的序列化撞不上):键的先后不影响结果,数字 `1` 与文字 `'1'` 不混。原来算得出的每一份 hash 不变(§0)。

## ⑨ 三点、独立复核结果、交付的三点(v1.2.0 · 卡片接口的工具包一侧)

应用弹确认卡、交付卡时从这里规定的位置读内容,agent 按这里写。这一节是应用(app-core)与工具包共用的合同:读法有两份实现(工具包 `pipeline_lib` 是参考实现,应用用 JS 自己实现),两边判得不一样就是 bug。

### ⑨-1 三点:正本最后一节 `{#commitments}`

task_plan / dossier / outline 正文的最后一节。确认卡上「请你重点看这三点」由应用从这一节读:标签由应用按位置写,只取每条的**内容** —— 卡上三点与材料里的三条逐字相同,是构造出来的,不靠比对。

写法(一个带锚点的 H2 标题,下面恰好三条编号列表,别的什么都不放):

```markdown
## 要你认的三件事 {#commitments}

1. **改动内容**：按你的意见，时间段从 2022–2025 改成 2021–2025；其余没有改动。
2. **最薄弱的依据**：分县的充电桩数据可能只有部分地市公布过。
3. **最可能出错的地方**：把私人桩和公共桩的数字混在一起。我会在每张资料卡片上标清口径，你可以抽查。
```

| 位置 | 标签 | 内容上限 | 写什么 |
|---|---|---|---|
| 1 | `改动内容` | 60 字 | 这一版比上次请用户确认的那一版改了什么;判断、范围、口径、比较对象的改动必须写明;第 1 版写「这是第 1 版」;没改写「没有改动」 |
| 2 | `最薄弱的依据` | 60 字 | 最站不住的一条依据,具体到哪份资料、哪个数 |
| 3 | `最可能出错的地方` | 80 字 | 最可能错在哪,最好写上用户能怎么抽查;资料汇编这一条写写作时最容易越过资料能支持的范围的地方 |

- **一条** = 一行 `<序号>. **<标签>**<冒号><内容>`,冒号是 `:` 或 `：`。**内容** = 冒号之后到行尾,去掉首尾空白。一条写在一行里:续行不属于任何一条。
- **字数** = 内容的 Unicode 码位数(Python `len(s)`;JS 用 `[...s].length`,不是 `s.length`)。标点、数字、字母、空格各算一个。
- 内容是纯文字:不许出现 `**`(加粗)、`[[`(引文占位)、`](`(markdown 链接)、`http://` / `https://`(网址);引号「」只用来引用户原话(§⑦)。`commitment_problems` 按这几样报「不是纯文字」,资料汇编上卡的 `gate_verdict.reason`(§③)同样。
- 这一节是正文,进内容 hash。改了三点 = 改了正本,原来的确认记录随之失效。
- **齐全**(应用弹卡前、`commitments_check.py` 都按这一条判;不齐全就不弹):
  1. 有这一节(交付那组:文件在,⑨-3);
  2. 恰好三条,都按本节的写法或下面的旧写法读得出;
  3. 每条内容不空、不超过上限;
  4. 标签与位置对得上:新标签必须在自己的位置;旧标签按位置认(见下);
  5. 这一节里除了三条与空行没有别的行。
- **旧写法照样认**(v1.1.2 及以前的项目;新写的正本一律用新标签):
  - `1. **<旧标签>**:<内容>`:第 1 条的旧标签含「口径承诺」或「改了什么」,第 2 条含「最脆」,第 3 条含「最可能错在哪」(如 `口径承诺`、`写作/返修期间我改了什么已批的`、`最脆证据`、`成品最脆的一处`、`最可能错在哪(可验证预测)`);内容取冒号之后。
  - `- ① <旧标签>:<内容>`(圈码按 ①②③ 的顺序):圈码之后第一个冒号(`:` 或 `：`)之前是旧标签、之后是内容;没有冒号时整段都是内容。
  - 旧标签不上卡:卡上的标签一律按位置由应用写。
- **空白**(v1.2.1 A2 联调):行首行尾、编号或圈码之后、冒号之后的空白,按 Python 的 Unicode 空白认(空格、制表符、全角空格、不换行空格、垂直制表符等都算),但不跨换行 —— 编号后面就换行的,下一行不算这一条。读内容与判「齐全」认法一样。
- **改流程**(只改了 `stages`,§①):那张卡只有一点,标签「改动环节」,内容 ≤60 字,由 agent 在卡上填(`changes`,§⑦)。任务计划的 `{#commitments}` **不动** —— 它留着上一次完整确认时的三条,那仍是复核拿来对照成稿的尺子;改动环节那一句同时写进这一版 `revision_log` 条目的 `what`。
- 参考实现:`pipeline_lib.parse_commitments`(每条给 `index` / `label` / `text` / `content`,`content` 是去掉旧标签之后的内容)与 `pipeline_lib.commitment_problems`(按「齐全」逐条列出毛病);命令行 `python -X utf8 scripts/commitments_check.py <正本.md>`(交付那份加 `--delivery`):齐全 → 退出码 0,否则 1 并逐条说明。

### ⑨-2 独立复核结果:`review/result.json`

独立复核(review-module)每做完一轮,结果写进这一份文件,固定放在 `<project>/review/result.json`,只放最新一轮。应用读它判断交付卡能不能出、卡上「独立复核」那一行写什么。

**成稿文件与内容 hash**(本节与交付记录共用这一个定义):成稿文件 = 项目里 `out/` 下一层(不进子文件夹)扩展名为 `.html` 或 `.docx`(不分大小写)的文件,不算以 `~$` 开头的(Word 打开文件时在旁边留的锁文件)和以 `.` 开头的;列的顺序是 html 在前、docx 在后,各按文件名排;与 cite_check 读的成稿是同一批;一个文件的内容 hash = 它全部字节的 sha256,64 位小写十六进制;路径写成相对项目文件夹、`/` 分隔(`out/<稿>.docx`)。重新生成一次就算改过(Word 版文件里带生成时刻,字节会变)。

```json
{
  "kind": "review_result",
  "format": 1,
  "round": 2,
  "reviewed_at": "2026-10-05T15:20:00-04:00",
  "report": "review/report-2.md",
  "files": {
    "out/新能源汽车下乡与县域充电设施.docx": "<64 位小写十六进制>",
    "out/新能源汽车下乡与县域充电设施.html": "<64 位小写十六进制>"
  },
  "counts": {"must_fix": 0, "tone_down": 1, "citation_or_format": 0, "checked_ok": 1},
  "findings": [
    {"severity": "tone_down", "round": 1, "status": "fixed", "location": "第三节第二段",
     "original": "带动全省县域充电设施翻番", "supported": "参加县增速更高",
     "fix": "改成参加活动的县增速更高，并写明只来自 3 个地市的数据"},
    {"severity": "checked_ok", "round": 1, "status": null, "location": "第二节第一段",
     "original": "2024 年，H 省县域公共充电桩达到 2.3 万台", "supported": "与资料卡片的数值和口径一致", "fix": null}
  ]
}
```

(示例只列了两条发现,所以抽查无误是 1;设计稿上「抽查无误 5 段」就是 5 条 `checked_ok`。)

| 键 | 类型 | 谁写 | 说明 |
|---|---|---|---|
| `kind` | `"review_result"` | 脚本 | 固定 |
| `format` | 整数 `1` | 脚本 | 格式版本;改格式就加一。应用不认识的版本按读不出处理 |
| `round` | 整数 ≥ 1 | 脚本(`--seal` 的参数) | 第几轮。第 1 轮是完整复核;之后每一轮核上一轮的发现改没改好、改动的地方有没有新问题 |
| `reviewed_at` | 带时区 ISO-8601 字符串 | 脚本(机器时间) | 这一轮封存的时刻 |
| `report` | 字符串 | 脚本 | 这一轮人读报告的相对路径 `review/report-<round>.md`(文件必须在) |
| `files` | 映射 {成稿文件路径: 内容 hash} | 脚本(按盘上文件算) | 这一轮复核的成稿;不手写 |
| `counts` | 映射,四个非负整数 | 脚本(按 `findings` 数) | 见下表;不手写 |
| `findings` | 列表 | 复核 | 每条发现,键见下表 |

| `counts` 的键 | 对用户叫 | 数什么 |
|---|---|---|
| `must_fix` | 必须改 | `severity` 为 `must_fix` 且 `status` 为 `open` 的条数:这一轮复核的成稿里**还在**的必须改的问题。交付门槛看它,必须是 0 |
| `tone_down` | 说法要收一收 | `severity` 为 `tone_down` 的条数(改没改都算;改没改看每条的 `status`) |
| `citation_or_format` | 引用或格式损坏 | `severity` 为 `citation_or_format` 的条数(同上) |
| `checked_ok` | 抽查无误 | `severity` 为 `checked_ok` 的条数:抽查过、没问题的段 |

| `findings[]` 的键 | 类型 | 说明 |
|---|---|---|
| `severity` | `must_fix` / `tone_down` / `citation_or_format` / `checked_ok` | 四档;内部叫法依次是必须纠正 / 降格改准 / 技术破坏 / 保留确认 |
| `round` | 整数,1 到本轮 | 哪一轮提出的 |
| `status` | `open` / `fixed`;`checked_ok` 为 `null` | `open` = 这一轮复核的成稿里还在;`fixed` = 早一轮提出、这一轮核过已改好(本轮提出的不会是 `fixed`) |
| `location` | 非空字符串 | 在成稿哪里(章、节、段) |
| `original` | 非空字符串 | 成稿原来的说法(摘一句);`checked_ok` 写抽查的那句 |
| `supported` | 非空字符串 | 资料能支持的说法或依据;`checked_ok` 写核对了什么;「无法验证」的写缺什么 |
| `fix` | 非空字符串;`checked_ok` 为 `null` | 处置意见:改哪句、改成什么 |

- 「无法验证」的问题按它的档位记、`status: open` —— 核不了就不算清零。「已驳回」的不写进来(写在人读报告里)。
- **对得上当前成稿** = `files` 的路径集合与盘上现在的成稿文件集合相同,且每个文件的内容 hash 都相等。复核之后成稿又改过(哪怕只收了一处说法)、重新生成过、多了或少了一个成稿文件 → 对不上,要再复核一轮。
- **交付门槛**(应用把关,§⑦):cite_check 全部通过 + 本文件读得出、`kind` 与 `format` 认识、对得上当前成稿、`counts.must_fix` 为 0。
- **怎么写**:第 n 轮开始复核之前先跑 `python -X utf8 scripts/review_result.py <project> --files <n>`,把复核的成稿文件与内容 hash 记进 `review/files-<n>.json`(这一轮已经开始复核 —— 有了 `review/findings-<n>.json` 或 `review/report-<n>.md` —— 或者已经封存、已经放弃,它就不再重记:成稿与记下的一样时什么都不改,不一样时拒绝 —— 成稿变了就是新的一轮。没封存的那一轮用 `python -X utf8 scripts/review_result.py <project> --abandon <n>` 放弃(写 `review/abandoned-<n>.json`;这一轮的发现与报告留在盘上、不进结果),再开第 n+1 轮,对现在的成稿重新复核;封存过的轮次不能放弃)。复核把这一轮的发现写成 `review/findings-<n>.json`(一个列表,每条按上表)、人读报告写成 `review/report-<n>.md`,再跑 `python -X utf8 scripts/review_result.py <project> --seal <n>`:盘上的成稿要与 `review/files-<n>.json` 记下的一模一样(复核期间改过成稿就拒绝封存:结果只能绑在被复核的那一版上 —— 放弃这一轮,开下一轮重新复核);n ≥ 2 时,与**最后一个封存的轮次** k 对照(k 与 n 之间的轮次都要已经放弃,有一轮既没封存也没放弃就拒绝封存):k 封存的结果里还开着(`status: open`)的每一条发现,都要在第 n 轮的发现里按 `round` + `location` + `original` + `severity` 找得到(档位不许改,状态可以变成 `fixed`),少一条就拒绝封存;标成 `fixed` 的,必须是 k 里有的那一条(同一档),而且成稿与 k 封存时不一样 —— 成稿没改,k 里还开着的就不能标成已改好;封存成功同时留一份 `review/result-<n>.json`(这一轮的存档,下一轮核对用;应用只读 `result.json`)。其余:脚本校验每条发现,按盘上的成稿算 `files`、按发现数 `counts`,补上其余的键,写出 `review/result.json`。发现写得不对、报告不在、没有成稿文件、`<n>` 比现有结果的轮次小 → 退出码 2,什么都不写。`review_result.py <project> --check`:对得上当前成稿且必须改为 0 → 退出码 0;否则 1 并说明原因;结果文件读不出 → 2。应用不调用这个脚本,按本节自己判。
- 参考实现:`pipeline_lib.deliverable_files`(成稿文件与内容 hash)、`pipeline_lib.review_result_problems`(结果文件本身的毛病)。

### ⑨-3 交付的三点:`library/delivery_commitments.md`

弹交付卡之前写好;交付卡上「请你重点看这三点」由应用从这里读。整个文件就是三点:没有 `{#commitments}` 锚点,不需要 frontmatter,最上面可以有一行一级标题:

```markdown
# 交付 · 要你认的三件事

1. **改动内容**：第四节标题按你的意见改了；没有改动任何判断。
2. **最薄弱的依据**：第三节参加县增速 41% 只来自 3 个地市的数据。
3. **最可能出错的地方**：2025 年数据只到三季度，全年数字公布后可能变化。
```

- 写法、上限、齐全的判据同 ⑨-1,只多允许最上面那一行一级标题(有 frontmatter 时在它之后)。
- 第 1 条写写作和返修期间改了哪些用户确认过的内容(判断、口径、范围、提纲结构),没有就照实写;第 2 条是成稿里最站不住的一处;第 3 条是最可能出错的地方。
- 交付卡上点了「先不交付」、回去改过之后,弹交付卡之前重写这份文件。交付后它留在项目里(随归档),下一轮任务能拿它核上一轮的预测。

### ⑨-4 「要聊清的三件事」:工作笔记 `clarify.yaml` 与任务计划里的对应字段(v1.2.1)

进度面板第一步「明确任务」里的「要聊清的三件事」(报告类型 · 研究范围 · 成稿形式)在任务计划还没写的时候就要有内容(设计稿 D05、D06)。应用按下表取:

| 时候 | 报告类型 | 研究范围 | 成稿形式 |
|---|---|---|---|
| 还没有 `task_plan.md` | 应用自己的报告类型卡记录:卡还没弹 → 还没答;卡在等用户 → 等你在卡上选;选了 → 研判型 / 综述型 / 先不定(先按研判型写) | `clarify.yaml` 的 `scope` | `clarify.yaml` 的 `format` |
| 有了 `task_plan.md` | frontmatter 的 `genre`:argument → 研判型,survey → 综述型 | frontmatter 的 `scope_brief`,原样显示 | frontmatter 的 `constraints.words_max` 与 `constraints.formats` 拼成一句(见下) |

- 「几 / 3」= 三格里有内容的格数;「还没答」「等你在卡上选」不算。
- 有了 `task_plan.md` 就三格都从任务计划取,不再读 `clarify.yaml`。任务计划的 frontmatter 读不出来,三格都留空、不回去读笔记;缺 `scope_brief`(v1.2.1 之前写的任务计划)或它不是 1–30 字的字符串,研究范围那一格留空。

**工作笔记 `clarify.yaml`**(项目文件夹根目录。名字取面板上「要聊清的三件事」的「聊清」;和 `references.yaml` 一样是项目根下的 YAML):

```yaml
scope: 县级，含乡镇，不含村
format: Word 版
```

- 一个 YAML 映射,只有两个键:`scope`(研究范围)、`format`(成稿形式)。值是一句用户的话,非空字符串,**≤30 字**(码位数,数法同 §⑨-1,首尾空白不算),照「对用户说话」写、不放内部词。没答的那件不写这个键(或写 `null`),面板显示「还没答」。
- 什么时候写:委托原话里已经写明研究范围或成稿形式的,开场时就写;用户在对话里答了,agent 马上写(或改),在弹报告类型卡之前 —— 就是说「记下了：……」那一句的时候(D06)。用户后来改口,照改。报告类型不写进来,它在报告类型卡上定、记在应用自己的记录里。
- 它是 agent 的工作笔记,**不是正本**:没有版本、没有确认记录、不进内容 hash;确认流程、`pipeline_status`、`cite_check` 都不看它。任务计划写出来以后它就不再被读,留着不用删。
- 应用读不出(文件不在、不是 UTF-8、YAML 写法有误、整个不是映射)就当没有;某个键的值不是 1–30 字的字符串,那一格按「还没答」显示;别的键不认。值是 agent 写给用户看的字,应用显示前可以像卡上的空一样用 `wording` 的 `scanStrings` 扫一遍,有命中的那一格不显示。
- 参考实现:`pipeline_lib.read_clarify`(读文件)、`clarify_problems`(格式毛病)、`clarify_items`(两格,读不出的那格为 None)、`clarify_panel`(按上表取三格,报告类型在没有任务计划时由应用填);命令行 `python -X utf8 scripts/clarify_check.py <project>/clarify.yaml`:格式对 → 0,不对(含读不出)→ 1,文件不在 → 2。

**任务计划里的对应字段**:
- 研究范围 = frontmatter 的 `scope_brief`(v1.2.1 新键,§①):研究范围一节 `{#scope}` 的一句话摘要 —— 地域与层级、时间段等 —— 一句用户的话,**≤30 字**,原样显示,例 `H 省县级，含乡镇，不含村 · 2021–2025 年`。它是实质字段:进内容 hash,改了要重新确认;只改流程时不许动它(§①)。`commitments_check.py` 对任务计划一并核它。
- 成稿形式 = `constraints.words_max` 与 `constraints.formats` 拼成一句:两段用 ` · `(空格、间隔号、空格)连 ——
  1. 字数段:`words_max` 是正整数(YAML 里写成整数)→ `约 <words_max> 字`;否则算读不出,省掉这一段 —— 小数写法(`8000.0`)、加了引号的(`"8000"`)、`true`、0 与负数都算读不出(v1.2.1 A2 联调写明;工具包一直这样读,应用照此对齐)。用户说「八千字左右」,`words_max` 写 8000。
  2. 格式段:`formats` 是列表,`html` → 网页版、`docx` → Word 版;两种都有写「网页版和 Word 版」(先网页版后 Word 版,不管列表里的顺序);别的值不显示;一个都认不出就省掉这一段。
  3. 两段都省掉 → 这一格留空。例:`words_max: 8000`、`formats: [docx]` → `约 8000 字 · Word 版`(D07);`formats: [docx, html]`、没有字数 → `网页版和 Word 版`。
- 报告类型 = `genre`(上表)。
- 参考实现:`pipeline_lib.panel_format`、`clarify_panel`。

**首页项目卡那一行**(设计稿 D03):`<类型> · <成稿叫法><字数> · <格式>` ——
- 类型:任务计划的 `genre` → 研判型 / 综述型;还没有任务计划、frontmatter 读不出、`genre` 不是这两个值 → 类型未定。
- 成稿叫法 = frontmatter 的 `report_name`(v1.2.1 新键,§①):**可缺**;写了就是用户的说法(内参、报告、研究报告……),一个 1–6 字的字符串(码位数,首尾空白不算);问过报告类型卡时与卡上的 `report_name` 一字不差。是实质字段,进内容 hash(只改流程时不许动它,§①)。没有这个键的任务计划(包括 v1.2.1 之前写的)照样有效;写了却不是 1–6 字的字符串,按没有显示,`commitments_check.py` 报出来。
- 字数 = 成稿形式的字数段 `约 <words_max> 字`。成稿叫法紧接字数,中间**不空格**:`内参约 8000 字`;没有成稿叫法就只有 `约 <N> 字`;没有字数就只有成稿叫法;两样都没有,这一段省掉。
- 格式 = 成稿形式的格式段(网页版 / Word 版 / 网页版和 Word 版)。
- 段与段之间用 ` · `(空格、间隔号、空格,同 D07);省掉的段连同它的分隔号一起省掉。还没有任务计划时整行只有 `类型未定`。
- 例(D03):`研判型 · 内参约 8000 字 · Word 版`;没有成稿叫法的已交付项目 `综述型 · 约 3000 字 · Word 版`;还在聊需求、没有任务计划 `类型未定`。
- 参考实现:`pipeline_lib.home_line`、`report_name_of`、`report_name_problems`。
