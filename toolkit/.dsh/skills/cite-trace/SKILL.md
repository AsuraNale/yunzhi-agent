# cite-trace · 第四步:撰写交付

> 前置:本项目流程里的材料(任务计划、资料汇编、提纲)都已确认。公理:**先卡后文** —— 写作期只用已有的资料卡片与参考文献清单,不引入新材料。路径约定见 AGENTS.md。

## 你在哪

最后一步。完成 = 用户在交付卡上点了「交付」+ 归档做完。用户在这一步随时可以看草稿、提意见 —— 草稿迭代是免费的(改 drafts 正本、重新生成)。**两种格式都生成**(网页版与 Word 版:应用的预览要网页版,交付卡两种都列);任务计划的 `constraints.formats` 记的是用户要拿到哪种,交付时告诉他那一种在哪。**篇幅按任务计划(第一步问过的,别再问)。**

## 这一步怎么走 —— 自由,但有出口

写作顺序(先难后易、先骨后肉)、要不要给用户看中间稿、分几轮生成 —— 自定或商量。唯一要求:出口契约全满足,写作纪律(下)每条在场。
**写作中发现缺资料 → 停**:回 evidence-card 补资料(资料汇编作废、重新确认),不许临场编、不许「先写完再补」。要大改提纲结构 → 先用决定卡问用户,再回 outline-cocreate。

### 成稿写完之后,按这个顺序(不许跳)

1. **生成**两种格式的成稿(E1),然后 `python -X utf8 "<toolkit>/scripts/stamp.py" "<project>/task_plan.md" --advance verifying`。
2. **交付前检查**:`python -X utf8 "<toolkit>/scripts/cite_check.py" --project "<project>"` 修到全过(E2)。你能修的先修好再跑;修法看 fix_hint,回正本改。
3. **独立复核第 1 轮**(E3,`review-module`):开始前记下复核的是哪几个文件 `python -X utf8 "<toolkit>/scripts/review_result.py" "<project>" --files 1`(写 `review/files-1.json`);复核把发现写成 `review/findings-1.json`、人读报告写成 `review/report-1.md`,封存 `--seal 1`。复核进行期间别动成稿:封存时成稿和开始时记下的对不上,脚本拒绝封存;动了就是新的一轮 —— `--abandon 1`,再从 `--files 2` 起对现在的成稿重新复核。
4. **改**:必须改的全改;说法要收一收、引用或格式损坏的也改。改了成稿就重新生成 → 再跑第 2 步 → 再复核一轮(先 `--files n`;第 n 轮把上一轮还开着的每条发现照抄过来核改好没有,再核改动的地方有没有新问题,封存 `--seal n` —— 上一轮还开着的发现少抄一条、改了档,或者成稿没改却标成已改好,脚本都拒绝封存)。**复核封存之后成稿一个字节也不能再动**:动了(哪怕重新生成一次)就对不上,要再复核一轮。
5. `python -X utf8 "<toolkit>/scripts/review_result.py" "<project>" --check` 退出码 0:复核结果对得上当前成稿,必须改 0 处。
6. **交付的三点**写进 `<project>/library/delivery_commitments.md`(E4),`python -X utf8 "<toolkit>/scripts/commitments_check.py" "<project>/library/delivery_commitments.md" --delivery` 退出码 0。例:

```markdown
# 交付 · 要你认的三件事

1. **改动内容**：第四节标题按你的意见改了；没有改动任何判断。
2. **最薄弱的依据**：第三节参加县增速 41% 只来自 3 个地市的数据。
3. **最可能出错的地方**：2025 年数据只到三季度，全年数字公布后可能变化。
```

   整个文件就是三点:最上面那一行一级标题可以不写,不写 `{#commitments}` 锚点(规格 §⑨-3)。
7. 发一句话:成稿写完了(章数、字数、引用、参考文献 —— 照生成时的元信息条与检查输出写),检查和复核的结果。然后调 `ann_gate_card`,只给 `id` 和 `kind`(`id` 写 `delivery-<第几次弹>`):

```json
{"id": "delivery-1", "kind": "delivery"}
```

卡上的成稿、交付前检查、独立复核的计数、三点都由应用读。应用弹卡前自己再跑一遍检查、读复核结果:检查没全过、复核结果对不上当前成稿、或还有必须改的,它不弹这张卡,退回给你 —— 照它说的补齐,不要绕。

用户回答之后:**交付** → 应用已写交付记录、把状态推进到已交付、存了成稿的档;你做归档(E5),说交付之后那句话。**先不交付,回去改**(`approved: false`)→ 照附言改(没附言就问改哪里),改完从第 1 步重来,三点按这一轮的改动重写。卡被退回 → 照 task-planner「卡被应用退回」。

## 对用户说话

> 用户是政策、公共事务、产业经济方向的研究员，不是开发者。本节管你**对用户说出口的每一句话**：普通消息、对话里的提问、进度汇报、阶段交接，卡上留给你填的空，以及给用户看的材料里你自己写的句子。
>
> 本 skill 其余部分用的是内部叫法（文件名、字段名、状态名、脚本名）。干活、写文件、跑命令时照旧用；**说给用户时换成下面词表的右栏**。确认卡、决定卡上的问题、按钮和标签由应用写，你只填卡上留给你的空，填的空同样按本节写。

**五条原则**

1. 不出现英文内部词、编号和文件名：argument、E4、task_plan.md、hash 这类。需要指代某个东西时，用它的研究员名称加版本，例如「任务计划第 2 版」。
2. 每个内部对象只用一个研究员名称：任务计划、资料汇编、提纲、成稿、资料卡片、参考文献清单。不要一会儿叫正本、一会儿叫 dossier。
3. 流程动作说成「确认 / 修改 / 重新确认」，不说落章、作废、重弹、推进 collecting。
4. 检查结果只说「有什么事需要你知道或决定」，不报检查项名，也不报 PASS/FAIL。
5. 方法论的动作说成它对报告的影响。例如不说「预注册」，说「先把几种可能的结论和判定标准写下来，结论就不会随着证据被挪」。

**引用怎么写**：用户的原话逐字照抄，放进「」或整段放进 `>` 引用块，前面写明这是「你的原话」或「委托原文」；文献和报告的标题放进《》。应用在弹卡前会扫一遍用词，并把卡上「」里的字和用户写过的话（委托原话、用户发过的消息）逐字核对：对不上的不算引用，照样算你的用词。所以卡上填的空里，「」只放用户原话；你自己的话（包括环节名、章节名）不加引号。

**研究流程的四个环节**：明确任务 · 收集资料 · 拟定提纲 · 撰写交付。确认点：第 1 次确认（任务计划） · 第 2 次确认（资料汇编） · 第 3 次确认（提纲） · 交付确认。

**这一步常说的几句**

- 开场这样说：「最后一步：撰写交付。按确认过的提纲写成稿，交付之前会做自动检查和一轮独立复核。」
- 自动检查的结果只说需要用户知道或决定的事，例如「有 3 个数字还没找到出处，我正在补」；你自己能修的先修好再说。全部通过时说「交付前的自动检查全部通过」。
- 转述复核发现时，严重程度说成：必须改 / 说法要收一收 / 引用或格式损坏 / 抽查无误；「八类曲解」说成「八类改写失真」。
- 写作中发现缺资料时这样说：「写到这里发现还缺资料，需要回去补；补完资料汇编要请你重新确认一次，然后接着写。」
- 弹交付卡之前，一句话说清成稿和检查、复核的结果，数字照生成时的统计和检查结果写，例如：「成稿写完了：5 章，8120 字，引用 42 处，参考文献 26 条。交付前检查全部通过，第一轮查出 2 个数字没有出处，我已经从资料卡片补上。一个没参与写作的助手复核过：没有必须改的，有 1 处说法收了一点。请你看看能不能交付。」
- 用户点了「先不交付，回去改」又没写附言：「好，先不交付。你想改哪里？」
- 交付之后这样说：「成稿已交付。这次用到的来源和还没补上的资料缺口已经存档，留给以后的课题。」

## 出口契约附注

**(E1) 生成与 liveness**
⭐ **骨架固定、样式可换**:`--theme plan`(默认,执行手册气质)/ `--theme classic`(宋体暖纸观感);主题在 `<toolkit>/templates/themes/`,只改观感不改结构。**`--cards` 要给** —— 元信息条(章节 / 引用 / 来源 / 卡数)**一律由生成脚本机器数**,不读正文自述(「成稿自述 21 卡、实际 23」正是这么漏的)。
⚠ 早期的生成脚本只有「标题或段落」两种,**表格 / 列表 / 粗体全不生成**(实测早期成稿 `<table>` 全是 0);现在补齐了,勿退回。**liveness 已探测**(references.yaml 每条记 `{state 五态, probed_at, probed_from}`;只有 failed(4xx/5xx)上成稿 ⚠ 角标,blocked / failed(net)记录在案不上稿),探测后**重新生成一次** —— 都在复核之前做完。

**(E2) 说给用户的数字从哪来**
- 章数、字数、引用、参考文献、资料卡片张数一律机器取值(生成时的元信息条 / cite_check / card_check 输出),不许自述 —— ⑩ 会拿 `cards/` 实际张数对账。
- ⚠ 「文内引用」只能抄元信息条,不是 cite_check ③:元信息条数**角标出现次数**(实测 62),③ 数**去重后的 http 外链**(实测 26)。文内角标是页内锚点,③ 只收外链 —— **③ 根本看不见文内引用**。填错了机器不会拦(⑩ 只对账卡数)。
- 每个数字都要知道量自哪个格式:量过网页版不等于量过 Word 版(实测:网页版表格 6 张,Word 版真表格 0、残留竖线 233,当时没拦住)。
- ✅ 金额可以正常写:`$249` / `$399` 在散文、同格多金额、跨格表格里都逐字生成,`$$…$$` 与 `$\alpha$` 仍是公式。唯一被牺牲的是 `$<数字>…$` 当行内公式(如 `$2x$`)—— 流程里不用这种写法。

**(E3) 复核结果绑的是成稿的字节**
`review/result.json` 记着复核时每个成稿文件的内容 hash;应用拿它和盘上的成稿比。复核之后改一个字、重新生成一次(Word 版文件里带生成时刻,字节就变了),结果就对不上,交付卡出不来 —— 要再复核一轮。所以 liveness 探测、最后一次生成都放在复核之前;复核发现的问题改完,一定再复核一轮。

## 写作纪律(活动级不变量)

- 正文引用一律占位 `[[R###]]`(登记表 id,生成时按出现顺序编号);**禁止裸 URL**;禁止「见证据卡X」当终点引用(D8);**引用弱 / gap 卡之前必须回源重验**,验不过就别引。
- **每个实质数字必须能回溯**到某张卡的 facts(带口径)或登记表条目 —— 写的时候就从卡里抄数字,不凭记忆(cite_check ⑤ 逐个扫)。
- 按提纲节点写:point / task 是契约,evidence 是弹药范围;超出 evidence 的论断 = 越卡声称。
- 成稿生成规则:tier B 转引标注、unverified 角标 `[n†]`、liveness ⚠(生成脚本自动处理,前提是登记表字段填对)。
- **机器的真实覆盖面**:链接层改动 cite_check ④ 会抓,**纯文字层改动机器抓不到** —— 靠正本纪律与独立复核,不是「反正会被拦」。
- 交付三点的「改动内容」写写作和返修期间改了哪些确认过的内容(判断、口径、范围、提纲结构);升版靠这条纪律,机器不拦。
- 卡上留给你的空写实;TOOL_OUTCOME_UNKNOWN → 原样再弹,禁止假定用户选了推荐项。
