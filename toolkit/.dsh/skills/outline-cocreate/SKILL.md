# outline-cocreate · 第三步:拟定提纲

> 前置:任务计划与资料汇编均已确认;方法论内容(判定标准、中途检查点)引用 `task_plan_ref`,不重复写。路径约定见 AGENTS.md。

## 你在哪

第三步。完成 = 提纲在确认卡上被用户确认。**这一步天生就是共创** —— 用户逐轮给意见、你逐轮改,别把它做成「我出一版你批一版」。

## 这一步怎么走 —— 自由,但有出口

**没有规定步骤。**先出全纲再细化、还是一节一节长出来、还是用户口述你落笔 —— 跟着对话走。每轮迭代:改正本 → `version` 加一 → `revision_log` 记明 → 改了的节点 `revision` 字段标动作(新增 | 深化 | 拆分 | 合并)→ 三点的改动内容写这一轮改了什么 → 自检:

```
python -X utf8 "<toolkit>/scripts/outline_check.py" "<project>/outline.md" --cards "<project>/cards"
```

用户在界面上看提纲(章节树、每节依据哪几张资料卡片、篇幅分配都由应用按 outline.md 显示),你不用另外生成网页、不贴路径。改完告诉用户这是第几版、改了什么、合计字数和目标对不对得上。

用户的意见(第二节太干、三四节合并)= **对当前提纲的迭代,不是确认**。
各节字数加起来和目标的偏差超出允许偏差只是提醒,但要报给用户,由用户决定调总字数还是调各节的分配。

### 用户说可以了:弹提纲卡

1. 自查:`outline_check.py` 无 FAIL;`python -X utf8 "<toolkit>/scripts/commitments_check.py" "<project>/outline.md"` 退出码 0;`node "<toolkit>/scripts/session_facts.mjs" --project "<project>" --json "<project>/out/session_facts.json"` 刷新会话事实(卡上读过的项目以外的文件由应用自己列)。
2. `python -X utf8 "<toolkit>/scripts/stamp.py" "<project>/task_plan.md" --advance gate3_awaiting`
3. 发一句话请用户确认提纲第几版、确认之后做什么。
4. 调 `ann_gate_card`,只给 `id` 和 `kind`(`id` 写 `outline-v<版本>`):

```json
{"id": "outline-v3", "kind": "outline"}
```

版本、合计字数与目标、没有资料卡片支撑的节、三点,都由应用从提纲读。弹卡之后、用户回答之前别动提纲。

用户回答之后:**确认** → 应用已写确认记录、推进到撰写交付;说一句交接的话,交棒 cite-trace。**先不确认**(`approved: false`)→ 接着改提纲(没附言就问要动哪里)。卡被退回 → 照 task-planner「卡被应用退回」。写作中要大改结构,先回这一步(见文末)。

## 对用户说话

> 用户是政策、公共事务、产业经济方向的研究员，不是开发者。本节管你**对用户说出口的每一句话**：普通消息、对话里的提问、进度汇报、阶段交接，卡上留给你填的空，以及给用户看的材料里你自己写的句子。
>
> 本 skill 其余部分用的是内部叫法（文件名、字段名、状态名、脚本名）。干活、写文件、跑命令时照旧用；**说给用户时换成下面词表的右栏**。确认卡、决定卡上的问题、按钮和标签由应用写，你只填卡上留给你的空，填的空同样按本节写。

**五条原则**

1. 不出现英文内部词、编号和文件名：argument、E4、task_plan.md、hash 这类。需要指代某个东西时，用它的研究员名称加版本，例如「任务计划第 2 版」。
2. 每个内部对象只用一个研究员名称：任务计划、资料汇编、提纲、成稿、资料卡片、参考文献清单。不要一会儿叫正本、一会儿叫 dossier。
3. 流程动作说成「确认 / 修改 / 重新确认」，不说落章、作废、重弹、推进 collecting。
4. 检查结果只说「有什么事需要你知道或决定」，不报检查项名，也不报 PASS/FAIL。
5. 方法论的动作说成它对报告的影响。例如不说「预注册」，说「先把几种可能的结论和判定标准写下来，结论就不会随着证据被挪」。

**引用怎么写**：用户的原话逐字照抄，放进「」或整段放进 `>` 引用块，前面写明这是「你的原话」或「委托原文」；文献和报告的标题放进《》。应用在弹卡前会扫一遍用词，并把卡上「」里的字和用户写过的话（委托原话、用户发过的消息）逐字核对：对不上的不算引用，照样算你的用词。所以卡上填的空里，「」只放用户原话；你自己的话（包括环节名、章节名）不加引号。

**研究流程的四个环节**：明确任务 · 收集资料 · 拟定提纲 · 撰写交付。确认点：第 1 次确认（任务计划） · 第 2 次确认（资料汇编） · 第 3 次确认（提纲） · 交付确认。

## 不变量

- **正本 / 显示分离**:只改 outline.md;用户看到的提纲由应用按它显示。
- 提纲的每个空 evidence 节点都是一次显式决定,不是偷懒出口。
- 卡上留给你的空写实;TOOL_OUTCOME_UNKNOWN → 原样再弹,禁止假定用户选了推荐项。
- ⛔ **不给用户出题**(同 evidence-card 的说明)。

## 确认之后又要改提纲

确认之后要改提纲(含写作中发现结构问题),或者资料汇编重新确认之后提纲要跟着再确认:照下面「重新确认一份已经确认过的材料」做(提纲推进到 `gate3_awaiting`),弹提纲卡照上面「用户说可以了」的 1–4 步。只改措辞、没动结构和判断的,用户可以直接确认。

**重新确认一份已经确认过的材料**(它要改,或者前面的材料重新确认之后它要跟着再确认一次)—— 三份 skill 用同一套做法:① `python -X utf8 "<toolkit>/scripts/stamp.py" "<那份材料>" --invalidate --why "<为什么>"`(旧的确认记录挪进 revision_log,它自己加一条,`v` = 当前版本加一);② frontmatter 的 `version` 加一,与那一条的 `v` 对齐;③ 改要改的地方,三点的改动内容照实写 —— 内容没动就写「没有改动」(可以带一句为什么要重新确认),只改了措辞就写「只改了措辞」,改了别的就写改了什么;④ `python -X utf8 "<toolkit>/scripts/stamp.py" "<project>/task_plan.md" --advance gate1_awaiting`(任务计划)/ `gate2_awaiting`(资料汇编)/ `gate3_awaiting`(提纲),再弹它的确认卡。
